# 第十五批 TDD和测试判据

测试应先证明自己会在目标错误上失败，再作为实现与重构的依据。对现有DSH，最有价值的不是增加用例数量或追求一个覆盖率数字，而是确保用例到达正确阶段、越过实际边界，并独立判断状态、用量和产物。

## 质量体系篇

Q27 p1–5先确定核心链路和风险，再分配纯逻辑、协议集成和故障测试。重点不应是模型写了多少，而是权限、异常可见性、历史消息顺序和并发写入这些关键路径有没有可复核判据。p6–10展示先审测试计划、确认mock和真实DB的边界，再逐场景落地；模型指出“mock了写库，却要求查到数据库记录”的矛盾，是值得保留的审查方式。

课程也有几处需要修正后吸收：

1. **短历史不一定能暴露截断排序错误。** p3指出错误查询为升序取前20条，p10却只给出三次发送，称该用例应因排序错误变红。若历史未超过20条，最早20条与最新20条再升序展示一致；不能保证抓到该bug。本地内存SQLite对同一张表比较两个查询，3行时都是1–3，21行时分别为1–20和2–21。这个探针只验证SQL条件，不是运行了课程项目。应构造超过实际窗口的数据，并断言最新保留、旧项淘汰及顺序。
2. **流正常结束不足以排除伪造成功。** p8–9将工具失败时仍能结束SSE作为主要检查，而原风险是异常后返回假数据。流不挂起是必要条件；还需验证错误是显式失败或按契约交给模型处理，不能伪装成真实工具结果，也不能把未完成回答落成成功。不同产品可有不同终止策略，不能统一要求done来证明安全。
3. **记录越权现状不等于允许越权。** p8的特征测试可以暂时记录既有缺陷，但必须与期望安全性质和未完成事项绑定。修复后旧行为用例变红只是迁移信号，应改为断言拒绝并保存修复前证据，不能把“越权可行”纳入长期的发布绿灯。
4. **替代库和调用方式限定证据范围。** H2并非MySQL；MockMvc也不等于真实网络请求。p9并列RANDOM_PORT、MockMvc与事务回滚，实施时必须确认究竟走哪条调用路径。服务线程发起的真实HTTP写入，不能仅凭测试线程带回滚注解就认为被统一回滚。本项目相应区分TestClient、真实回环socket和正式服务。
5. **测试分层不能成为禁止测试的分类法。** 含HTTP或SQL的模块仍有可独立测试的协议映射与纯函数；是否mock标准库取决于目标故障，不应绝对禁止。比如模拟提交失败、时钟和进程故障，需要说明替换点并用行为、对照和真实路径补证。
6. 双模型review可能补充视角，但不同名字不保证错误相互独立，80–90%的经验分工也不是可靠性指标。Review要固定版本、说明假设、复现反例；规则写进说明文件不保证每次被执行。故障注入也不必等维护期，本项目发布前就需要取消、崩溃和提交失败验证。

作者p11评论建议规范独立成文档，再由入口文件引用；这一点符合当前AGENTS地图与分项规格的做法，不需要把所有规则塞进一个长期膨胀的文件。

## TDD实战篇

T19 p1–8按任务依赖执行红、绿、重构，用GitHub URL解析展示先得到可编译但按行为失败的测试；p8–12引入可注入HTTP客户端和本地Mock Server；p13–18讨论worktree、规范变更和独立验收。最有用的两点是：未实现行为的失败不同于编译/导入失败；需求理解发生变化时，规范和受影响任务应同步增量更新，不能仅补代码。

需要限定的表述：

- 测试先写并非不可逾越的真理边界。错误规格、遗漏输入、弱断言和评分器缺陷仍会共同给出绿灯。p16评论也承认模型可能修改测试；仅限制一种写工具不能代表封闭所有编辑路径。固定测试哈希、review差异和独立回归更直接。
- p9空实现时404用例已经通过，应检查它断言的是正确状态/错误码，还是只检查有任何错误。未实现也会报错，不能据红阶段的总退出码推断每条负例有效。PDF没有展示该断言的完整实现，因此此处是审查要求，不判定作者仓库存在已证实缺陷。
- p8称23条测试足以放心大幅重构，强度过高。只能证明这些判据仍成立；接口兼容、遗漏边界、性能与并发还需对应验证。p17建议80%覆盖率也不能抓住执行了代码却没有有效断言的问题。
- 可注入HTTP依赖有利于验证，但不必为测试把内部客户端永久公开可变。测试配置入口与生产URL、凭证和网络权限应分开；本地Mock Server证明协议行为，不证明真实服务商兼容或认证可用。
- p13的worktree并行不隔离共享数据库、端口与依赖；无文本冲突的合并也可能有语义冲突。[P]是待验证的依赖判断，不是并发安全证明。当前完整测试冻结实现worktree、报告另写worktree，正是为避免被测代码中途变化。
- p15–18评论强调独立验收、增量更新任务和行为边界，应保留；不是为追求形式上的TDD而拒绝修正错误测试，也不是让功能代码自行决定所有预期值。

## 本轮对应的验证改进

| 风险 | 本轮落点 | 仍不能推出什么 |
|---|---|---|
| 边界没有被实际跨过 | HA87覆盖499/500/501、999/1000/1001及真实稀疏sequence | 不证明大库扫描性能已达标 |
| 失败发生在错误阶段 | HA89先确认Provider已到达，再触发Run单调截止、墙钟截止或响应超时 | 不把SDK初始化失败算发送后的超时验证 |
| 评分器和实现一起误判 | HA88独立匹配完整数值与单位，失败无产物不算无误报成功 | 固定脚本语法不是任意自然语言语义裁判 |
| 只验证单个状态未验证原子关系 | HA85注入终态写入故障，检查票据、事件、Run、产物回滚 | 不承诺外部Provider与SQLite构成分布式事务 |
| 错误分类依赖原始异常文字 | HA86按生命周期阶段映射固定类别，以白名单处理桥返回 | 阶段正确不等于初始化慢的根因已经定位 |

各任务保留基线行为失败、反例文件哈希、突变的具体失败点与测试范围；等价突变、脚手架错误和环境超时不混作业务保护。完整verify中的浏览器失败也单独保存，不用定向通过数相加替代完整结果。

## 后续测试计划

优先完成当前固定版本的完整运行和独立复审。若浏览器失败重现，按服务端最后body、浏览器requestfinished、DOM/load及实际断言分别定位，先确认失败层再改实现；不自动放宽所有等待。

之后再补压缩前后证据完整性的独立样本、模型输出的语义反例及大历史详情的性能测试。每项都应有“故意移除哪道保护会在哪个断言失败”的说明，同时记录无法覆盖的情形。测试数量、覆盖率、变异数和真实模型少量成功各自保留含义，不能合成为一个模糊的生产可靠性分数。
