# 第十三批 部署容量和数据设计

部署设计应该记录当前瓶颈、测量办法和演进触发条件，不按用户人数直接推导“无需性能验证”。当前DSH是单工作进程的受控纵切；本轮首先需要解释浏览器回归失败、完成独立复审，而不是引入K8s、缓存集群或更换数据库。

来源：`架构设计/08 - 05｜架构设计（下）：部署架构、性能预判与数据设计.pdf`，14页，SHA-256 `030a15b3258e99e88bb7fea9e70921ab74ee760bcee1ac01f9c1cd1914cce4e5`。全文阅读含评论，第4页容量表已渲染核对；累计37篇417页。项目代码对照4b8ec1e。

## 课程主线

p1–3为50人内部应用设计模块化单体，拆清静态资源、业务数据、缓存和向量检索职责；p3–7列出潜在瓶颈与分阶段演进；p7–9梳理业务表与引用关系；p9–12给出索引、分页和数据规范；p13–14补充作者对双数据库选型、规范文件拆分和部署形态的解释。

最有用的是写出“当前不做什么”和触发条件，避免为了未来假想规模立即拆微服务。消息与证据块之间保留来源关系、唯一约束放进数据库、增长较快的事件使用稳定游标，这些也适用于本项目。

## 不应照搬的结论

1. p4认为50人规模无需处理所列性能瓶颈，另将慢模型占线程定性为需要处理的稳定性问题。两者在原文中有所区分，但仍需具体负载测量。人数不是负载模型：单个长任务、并发突发、大产物和缓慢SDK启动都可能影响少量用户。表中的并发、百万级数据和线程池数是示例假设，不是经过本项目压测的容量边界。
2. p6把LLM异步化与必须从SSE改成轮询/WebSocket绑定过强。后台队列和前台事件传输是不同层，可以保留SSE并从持久事件流续传。Redis会话共享也不自动解决运行所有权、事件顺序、取消路由、重连与幂等。
3. p10–12的“禁止NULL、UUID、数据库外键”“所有删除字段必须进索引”等是示例团队规则，不是通用正确性结论。用0代替未知用量会破坏本项目unknown语义；取消现有唯一约束或外键也会改变完整性保障。索引应由实际查询计划、选择性与写入代价验证，不能因缺deleted列就断言索引无效。
4. 固定1536维、必须HNSW和按人数切换Qdrant，不应成为本平台默认架构。向量模型、维度、距离度量、索引参数和召回质量需要配套验收。作者p13也承认最初双数据库选型并非必要，直接使用PostgreSQL同样合理。
5. gzip对静态资源可能有益，但不能直接推广到模型协议和实时流。本项目聊天Provider流明确拒绝Content-Encoding，以防解压放大；这是不同的方向和信任边界。流式代理的缓冲与首事件延迟应单独验证。
6. 把规则写进CLAUDE.md是沟通与约束输入，不是自动执行保证。数据库约束、测试、静态检查和发布门禁仍需真正执行，不能用“模型读过规范”替代。

## 当前项目的容量地图

| 位置 | 已核对的机制 | 需要测量或补齐的边界 |
|---|---|---|
| `backend/app.py:31` | 同一DB由flock拒绝第二个服务实例 | 不能只加多个副本；跨进程执行与取消所有权尚未设计 |
| `backend/service.py:925`附近 | 一个worker依次扫描并execute排队的根Run | 长Run会占住执行位；应测排队时间，而不是仅看运行耗时 |
| `backend/store.py:32` | 单SQLite连接配RLock；事务保护状态、事件和产物 | 大范围读取可能持锁较久；外部直连不受这把Python锁保护 |
| `backend/store.py:264` | events按Run和真实sequence游标，每页500，已有复合主键 | 分页正确性不等于大库延迟已达标 |
| HA87 `_plan_history` | 详情完整扫描历史，修复后页计划遗漏 | 每次详情仍为O(历史事件数)，频繁轮询的成本需实测 |
| DSH bridge与Provider | 分开初始化阶段和发送后等待；每个Run有截止、取消和账本 | 60秒初始化容忍不是启动性能优化；unknown不能解冻重试 |
| 浏览器端 | Chromium真实HTTP临时库验证 | 本轮有导航load超时，静态200不等于页面完成；根因未定 |

例如单worker平均每个Run占用时间为T，则仅该执行位的理想吞吐上限约为1/T；这只是容量关系，不是本机实测。若其中包含模型等待，人数少仍可能排队。直接增加worker可能破坏现有单连接、预算、取消和子进程清理边界，应先设计并发契约。

## 建议的测量顺序

先记录队列等待、SDK启动、Provider等待、工具、发布、退出清理的单调时长；内容仍只存元数据。随后用合成Provider固定延迟，分别增长Run数量、单Run事件数和工具返回量，检查P50/P95/P99、取消响应、锁等待与内存峰值。不要把真实模型随机延迟和本机负载混成一个“平台性能”分数。

发布仍按固定代码、依赖、配置和实际监听PID核对；已有健康200只证明存活，不替代业务验证或发布身份。没有完成上述测量前，不承诺人数容量、并行加速或需要换数据库。本篇只增加研究记录，没有实施缓存、拓扑迁移、参数放宽或在线重启。
