## 结论一览

| 主题 | 可采纳原则 | 本项目边界 |
| --- | --- | --- |
| 状态外部化 | 长任务需要可读、可修改、可恢复的外部状态，而不是依赖窗口历史 | 产品 Task/Run 继续是权威状态；`plan.md`、`exec-plans/` 和 `harness/tasks.json` 是研发治理状态，二者不得混用 |
| Plan Mode | 重型规划只为复杂、跨会话任务启用；全程问题不强制写计划 | 不能用 Prompt 替代控制面状态机、权限或原子写入 |
| Error Recovery | 工具失败应产生带错误码、建议下一步的结构化恢复信息 | 只允许规则/证据驱动的提示；未知业务错误不能伪装成已解决 |
| System Reminders | 软提醒可打断重复失败或无进展探索 | 先有硬上限（turn、时间、费用、单工具调用）和取消；指纹提醒不能充当安全保证 |
| Middleware / Approval | 在实际副作用前统一拦截，采用 `allow / ask / deny`，审批与动作摘要绑定 | 无审批、过期、取消、输入摘要变化或租约失效均拒绝；绝不把高危命令黑名单写死为唯一防线 |
| Subagent | 主 Agent 委派高噪声探索，子 Agent 返回有界、可验证的摘要 | 子任务的工具、资源、预算必须是父项的子集；探索者默认只读；父 Agent 不因摘要而免除证据核验 |

## 逐篇阅读要点

### 13｜状态外部化与持久化记忆

- 区分短期 Working Memory、任务级 State、跨任务 Episodic Memory 和长期检索；压缩上下文不能取代可恢复任务状态。
- `PLAN.md` 负责宏观目标与约束，`TODO.md` 负责细颗粒执行。用户能直接改状态，使人机协同具备可见性。
- Plan Mode 应为按复杂度开启的策略，不应让一次简单查询产生冗余计划。
- 材料也指出工作区已有完成计划、任务切换和状态清理是边界问题；应归档或版本化，而非无限复用同一份清单。

本项目采纳：将 Team Task 的 requirements、scope、stop conditions、Gate 与 Handoff 持久化为可审计对象，且与一次 Run 的易失上下文分离。拒绝采纳：把 Markdown 或模型提示视为唯一权威状态。

### 14｜上下文感知的错误恢复

- 原始 Tool Error 对模型通常不可操作；恢复信息应明确失败类别、不可重试原因、推荐的下一步和需要人工介入的条件。
- 示例用 `read_file`、`edit_file`、`bash` 的错误匹配注入恢复提示，说明了“错误结果 + 行动建议”的价值。
- 材料明确承认字符串匹配脆弱；生产实现应使用稳定的领域错误码或标准系统错误，而非依赖中文错误文案。

本项目采纳：定义错误恢复契约时绑定 `error_code`、`recovery_class`、允许的下一步及证据。拒绝采纳：自动让低价模型解释未知错误并直接授权下一步；这会扩大数据与执行边界。

### 15｜System Reminders 与防止死循环

- 重复失败会造成近因偏差和局部目标执念；在下一次模型决策前注入短、明确的提醒比埋在长 System Prompt 中有效。
- 示例以工具名和参数指纹统计连续失败，在阈值后要求改策略或转人工。
- 材料的讨论进一步指出：硬预算、最长 Turn、单工具上限才是确定性熔断；严格哈希会被路径或空格变体绕过。

本项目采纳：把 Reminder 定位为可观测、可评测的软干预；把停止、取消和预算耗尽视为硬边界。后续实现应规范化可比较参数，并以“无可验证进展”而非单一 MD5 判断探索螺旋。

### 16｜Middleware、审批与防御纵深

- 唯一合适的截断位置是工具调用已被解析、但副作用尚未发生的执行边界；业务工具本身不应耦合审批通道。
- 本地可销毁沙箱可降低探索风险；远端共享系统仍须采用显式权限和人工审批。
- 审批必须绑定动作、参数摘要和任务；等待审批要有超时、拒绝默认和取消清理。单进程全局内存审批表不适用于多实例生产环境。

本项目采纳：继续使用 Policy Gateway、不可扩张的有效权限和 Evidence；新 Team Gate 的 `pass/reject/needs_human` 与高危 `ask` 是不同概念，不能混同。拒绝采纳：仅凭正则黑名单判断所有危险命令，或无限期阻塞等待飞书回调。

### 17｜受限 Subagent 委派

- Subagent 的主要价值是上下文隔离：探索噪声留在 Child，主 Agent 只接收浓缩报告。
- 作为普通受控工具的父子委派（delegate-and-return）适合单次探索；共享任务板、P2P 协商和多评审投票属于更高阶 Team 编排。
- Child 的能力应小于父项，阅读/检索角色默认不给写入权限，并设置独立 turn/time/budget 上限。
- 同一轮多个 Child 可以并行，但主流程通常仍等待它们完成；“后台并行且主流程继续”需要显式 job/Task/Inbox 协议，不能假设普通工具调用自然具备。

本项目采纳：Team Task 与 Child Task 要传递父级 scope、资源、权限、预算和 Gate，且 Child 只可收窄。拒绝采纳：把模拟并发、未授权模型调用或纯摘要报告表述成真实独立 Agent 成果。

## 与用户提供的 Agent Team 设计的合并

用户提供的 Agent Team 设计补齐了上述单 Agent Harness 没有覆盖的组织语义。其关键不是“更多聊天”，而是：

1. `Workspace → Channel → Thread/DM` 限定可共享的上下文范围；
2. `Task → Handoff → Gate` 固定目标、责任、证据与验收；
3. Inbox、work mark、execution lease 与 freshness 检查防止重复运行和过期答复；
4. Session/Computer/Agent Revision 把会话上下文、执行位置和版本演进分开；
5. Team 关系是可审计的委派输入/输出约定，而不是隐式“谁擅长什么”的模型猜测。

## 对 HarnessAgent 的实施顺序

1. **HA-0037 - Team Task Handoff / Gate 最小纵切**：独立于既有 Product Task/Run 的本地协作对象；包含原子 claim、要求冻结、范围/停止条件、追加 Handoff、提交、Gate 三出口和父项阻塞规则。
2. **HA-0038 - Inbox / work mark / execution lease / freshness**：按用户决定暂缓；它仍要求 Workspace/Channel/Thread 的身份与权限语义先冻结。
3. **HA-0039 - Recovery / Reminder 证据内核**：已完成结构化错误、规则候选恢复、重复失败/无进展信号、硬预算与转人工；不自动执行未经授权的补救动作，且必须接回 Handoff + Gate。
4. **HA-0040 - Computer / Session handoff / Agent revision**：在明确身份、权限、Daemon 和迁移数据范围后实施；不把本机凭据或工作目录迁移伪装成 Server 状态。

这些阶段不会改变当前 P0 CSV 分析契约，也不会启用外部模型、外部资料、真实多 Agent 或自动语义检索。
