## 0. 先给结论

下一步最值得做的，不是再接一个框架、扩大工具池或开启向量库，而是把当前 DSH 从“能受控地跑完并交付草稿”，推进到“能说明答案依据、遗漏和不确定性”。

推荐一个窄业务闭环：**付款条件核对：期限、触发条件、例外、冲突**。先建立固定评测与结构化结果，再接证据覆盖和无进展停止，最后做受预算约束的上下文组装。继续使用官方 DSH Loop、现有平台预算账本和两个只读工具，不重写引擎。

本次用真实 DSH SDK、合成 Provider 和临时 SQLite 做了三个探针：

1. 原文是“验收后30天付款”，合成答案改成“300天”，只要引用读过的 `clause-1`，仍会发布为需人工复核的草稿。
2. 同一个条款重复读取八次，直到尝试第九次模型调用时才触发硬上限；没有提前的证据进展停止。
3. 四个条款都命中“付款”时，只返回前三个，第四个里的“质量争议时暂停付款”没有被这次搜索带回；系统仍可发布一个引用合法但覆盖不足的草稿。

## 1. 第01讲：Loop 的职责是裁决，而不只是循环

### 课程讲了什么

课程区分单次任务内部的 Agent Loop，与更外层的工程迭代循环。它提出五个工程支柱：硬预算和独立验收、模型提议与系统执行权分离、显式状态与阶段、可恢复检查点、有界并发与隔离。C1 第7页的状态图尤其重要：模型说“完成”之后还要经过独立验证；工具执行前可以拒绝或等待人工批准。

其中有三个容易混淆的概念：

- **结束不等于完成**：模型没有继续调用工具，不代表用户目标已经满足。
- **有界不等于高效**：最多八轮能防无限运行，却不能阻止前七轮都浪费在同一个动作上。
- **保存聊天不等于可恢复**：执行位置、未决动作、已发生副作用、预算和权限版本必须另有真相源。

评论区关于独立验收的补充值得吸收：Checker 应直接读取原始输入和交付物，独立执行检查，而不是只读执行者写的“我已验证”。多个评审如果共享前一个人的结论，也不能算独立证据。

### 对照当前实现

DSH 已经把裁决权留在平台：`backend/dsh_runtime.py:157` 的取消/时间检查、`:167` 的模型次数上限、`:191` 的持久预算包装、`:209` 的工具许可、`:244` 的事务内最终发布检查。`backend/business_budget.py:120` 先预留，`:154` 标记发送，`:174` 结算；未知用量不冒充零消耗。

但是完成判断仍较窄：`dsh_runtime.py:238` 起只验证结果包、已读证据和引用集合，没有逐项检查付款期限、触发条件和例外是否齐全。进程重启会失败收尾而非自动续跑（`:260`）。后者是明确的安全选择，不应为了“可恢复”四个字贸然改为重新请求模型。

### 应吸收什么

增加“关键事实槽位 + 未解决缺口 + 可机械验证的完成条件”。保留当前硬预算；在硬上限之前识别重复动作和没有新证据的轮次。业务结果单独记录完整/部分/冲突/待人工，不新增第二套 Run 状态机，不把生成完毕升级为审查通过。

## 2. 第02讲：工具应该有六类契约

### 课程讲了什么

六类契约可以理解为工具完整生命周期的六个问题：

1. **设计**：一个工具究竟做一件什么事？读、改、删不应藏在同一个模糊入口里。
2. **决策**：描述要帮助模型区分何时使用、何时不用，明确参数语义和相似工具的差别。
3. **拦截**：只读性、副作用、风险、角色、幂等性应是机器元数据，不依赖模型自行判断。
4. **执行**：状态在服务端；重复操作不能重复发生副作用；长事务需要补偿或对账。
5. **反馈**：可恢复错误、永久错误、成功分开；反馈是受控错误码和行动选项，不是原始异常堆栈。
6. **资源**：工具输出有大小和时间预算，大结果有分页或受控回读，不能无限塞进上下文。

MCP 解决通信不等于替 Host 完成上述六项。接入一个外部工具服务仍需要平台自己的许可与数据边界。

### 对照当前实现

DSH 的两个工具已经原子且只读，参数字段集合、长度、条款归属均在 Python 端检查（`dsh_runtime.py:209`）。搜索最多三块、读取一块，切块上限为1500字符（`:151`），并非无界返回。

缺少的是统一的、版本化的工具描述/元数据快照和可恢复反馈协议。`dsh-adapter/platform-plugin.mjs:45` 的描述较短；参数只有 string/required，平台侧更严格。`backend/dsh_provider.py:43` 校验工具名称集合正好是两项，但没有机械绑定完整描述和参数 Schema 的版本摘要。`adapters/dsh.py:61` 起的认证后执行错误会进入共享错误列表、最终使 Run 失败；这不是课程中的“错误反馈后受控纠正”闭环。

### 应吸收什么

先只给现有两工具补齐注册元数据、输入/输出契约、版本摘要和限额，不建设通用工具市场。区分“检索无结果”“参数可纠正”“权限拒绝”“基础设施故障”。纠错必须计入既有模型次数、时间和 Token 总账；权限拒绝、未知计费、取消、状态损坏仍硬停。

只读搜索重复可按资源版本复用结果，但不等于给未来外部写工具实现了幂等。将来若引入外部写操作，应沿用平台事务/收据治理，并另外设计服务商幂等键、outbox 或结果未知时的对账，不承诺跨系统 exactly-once。

## 3. 第03讲：缩小候选集合，而不是教模型从海量工具里猜

### 课程讲了什么

工具越多，定义越占上下文，相似描述越难区分。课程建议核心工具常驻、领域工具按角色加载、冷门工具按需召回；描述先写触发条件和互斥边界；故障工具单独熔断，不让一个故障拖住整条任务。

工具召回可以组合名称、描述、领域标签等信号；形式化工具名经常适合精确匹配，并非凡是检索都必须上向量。评论还提示了动态工具数组对前缀缓存的影响，以及“拆成多 Agent”只是把工具选择问题上移成角色选择问题。

### 对照当前实现

DSH 只暴露两个工具，已经是非常小的候选集。`provider_payload` 和 `tool_call` 两端都检查允许集合；不是仅把危险工具从提示词里隐藏。当前没有113个工具的瓶颈，投资工具检索、动态角色或多 Agent 路由的收益未经证明。

现阶段优先改的是描述：明确 `search_document` 是字面匹配、仅返回前三项、不等于完整覆盖；`read_clause` 的 ID 是平台证据块编号，不是原文条号。初始 prompt 已写了一部分（`dsh_runtime.py:232`），应与工具 Schema 同源。

### 应吸收什么

保留最小候选集和执行端独立授权；以后新增工具先证明任务确实需要。工具级熔断只在出现真实、可独立恢复的外部依赖后再做，且不可把“故障暂时不可用”当成“权限撤销”，也不可在隐藏工具后默默放弃必需检查。

“最多20个”应作为待评测的工程起点，而不是数学定理；见第7节的课程修正。当前不需要为了符合课程结构造出空的 L1/L2/L3 工具平台。

## 4. 第04讲：格式校验之后，还要做业务校验

### 课程讲了什么

它区分提示词要求、JSON语法模式和约束结构输出，核心提醒是：合法 JSON、合法类型和枚举，都不能保证事实正确。工程侧应验证字段约束、跨字段关系和业务规则；失败反馈要精简，修正次数有界，关键字段失败转人工，非关键字段才考虑安全降级。

这个思路应该进一步拆成四层：

1. 协议/语法完整；
2. 类型、范围、字段和跨字段约束成立；
3. 引用确实属于这份资料，原文片段/数值能回查；
4. 结论确实受到证据支持，关键例外没有遗漏。

第三层不能自动推出第四层。Pydantic 或 JSON Schema 能执行已编码的规则，不能凭类型检查证明任意法律、商业或因果结论正确。

### 对照当前实现

DSH 已做 Provider响应完整性、工具名、参数形状和 usage检查（`dsh_provider.py:50`），结果包也有 Schema。但 `specs/v1/dsh-runtime.schema.json` 的 result 主体仍是自由 `text`，没有 claim/quote/value/status 等业务字段。

本轮“30天→300天”反例经过了真正的两轮 DSH 和工具回传；平台收到包含30天的证据，最后依然按契约发布带300天的草稿。它证明的是当前验收边界，不是说真实豆包必然犯这个错误。

### 应吸收什么

先为一个业务场景设计结构化结果：每个槽位有状态、声明、来源片段和未解决问题。平台签发来源定位，验证字面摘录、数值/单位/主体、冲突和必要槽位。缺证据允许明确 `unknown`，不能为了填满 JSON 猜答案。

建议只存简短的证据说明，不要求模型输出隐藏推理过程。模型复核若后续引入，只是单独计费、校准后的质量信号，不是确定性裁决替代品。Provider 的结构化输出能力尚未在此路径验证，不能直接打开参数就宣称接入完成。

## 5. 第05讲：管理上下文的组成，而不仅是扩大窗口

### 课程讲了什么

课程把上下文分为：稳定规则 L0、当前任务状态 L1、检索与记忆 L2、历史与工具日志 L3。状态真相保存在外部，每轮读取投影；高优先级规则不能被历史挤掉；低优先级内容先去重、限量，再考虑摘要和按需回读。

渐进压缩的重点是按重要性而非盲目删早期消息；工具大结果可先存为受控引用，而非每轮重复携带全文。首尾提醒和稳定前缀是提示组织策略，不是权限边界。评论提出了一个有价值的反例：减少输入 Token 但破坏缓存、引入摘要模型调用和重新读取，实际成本可能更高，因此应比较全链路成本与质量。

### 对照当前实现

原版聊天 Runtime 的 `_context` 取最近 `max_turns*2` 条（`backend/agent_runtime.py:274`）；system prompt 通过独立请求字段进入适配器。这不是完全没有上下文管理，但不是课程中的分区编译和证据保留策略。

DSH 平台桥把上游提供的消息逐项映射（`dsh_provider.py:17`），没有平台级 L0–L3 的选择/覆盖报告。`platform-plugin.mjs:21` 声明64000上下文、Task也填64000，但此发送路径未见对完整请求 Token 做独立的64000上限核验。网关256KiB字节限制、文档20000字符限制、调用前账本预留是其他维度的保护，不能互相替代。

2000万 Token 是整个 Run 的累计上限，不是每次上下文应该填满的目标。当前真实请求采取容量上界保守预留，不应在没有可靠计数和边界证据前换成乐观字符估算。

### 应吸收什么

做一个纯函数式的上下文组装器：输入可信规则版本、任务状态、已验证证据引用和历史；输出发送消息及各部分占用/删减原因。先去重和结构化摘取，再决定是否需要模型摘要。正在执行的 tool-call/result 对不能被拆散；平台规则和用户确认的任务约束不能被普通文档注入覆盖。

暂不启用后台压缩、记忆分类或其他辅助模型调用。未来若启用，必须走同一本预算账、同一个发送边界和取消链，并计算它是否真的节省端到端成本。

## 6. 第06讲：规则必须可靠到场，但到场不等于执行正确

### 课程讲了什么

课程按约束、事实、偏好、经历分类存储，再用规则、关键词、语义、实体关系分路召回；并发取候选，按优先级分配上下文。关键不是“必须四路”，而是**不可把硬规则是否出现交给相似度排名**。

正文末尾的思考题也暴露了上游依赖：规则按 domain 注入，如果 domain 本身由模型猜错，硬召回仍可能漏规则。附录给出了正确边界：让规则在上下文出现，只是帮助决策；预算、数量和审批等硬条件仍要在工具执行前校验。

### 对照当前实现

平台已有 Memory Plane：显式 Source/Fact、有效时间、撤回/替代/删除、FTS关键词及有限图关系；`backend/memory.py:64` 的 semantic 状态始终不授予运行权。这些不应被写成“我们没有记忆模块”。但 DSH 没调用这套 Memory API，也没有跨会话用户规则注入。

DSH 现有预算和工具白名单本来就在代码里，不依赖向量库召回。当前的检索风险是**文档关键证据覆盖不足**，不是已发生“安全白名单被向量漏掉”。合同里的付款例外是待核对事实；平台的“不能访问任意文件”是可信执行政策，两者不可混成一个可由模型改写的 CONSTRAINT。

### 应吸收什么

第一阶段先用人工确认/平台登记的业务检查清单，不用模型自动把文档文字提权成规则。以用户确认的任务类型、资源范围和工具能力确定适用规则；不确定时澄清或拒绝执行，不只依赖自然语言 domain 分类。

硬约束必须有完整性检查：适用规则过大、冲突、版本失效或无法装入上下文，就缩小任务或转人工，不能悄悄截断。软事实才参与TopK排序。之后如接 Memory，必须重新落实主体、Bank范围、来源有效期与删除传播；不能把另一仓库的用户隔离当作本平台已具备。

## 10. 下一步实施顺序（全部是建议，尚未实现）

### A. P0：冻结业务验收口径，再做结果与证据闭环

**解决问题**：当前“正确引用＋错误值/遗漏”仍是技术成功。

**最小范围**：只处理“付款条件核对”，用户确认目标模板；检查期限、触发条件、例外、冲突四个槽位。模型可提议拆解，平台不得把模型自行删掉的槽位当作目标已完成。

**接入点**：`dsh_runtime.py:238` 发布之前，增加版本化业务结果及独立验证器；`dsh_provider.py`/plugin增加受控结果协议，Provider能力另测。复用既有Artifact/Task/Run，不修改上游Loop。

**建议结果内容**：每个槽位为 `supported/unknown/conflicting` 之一；有声明、单位/主体、平台来源ID与片段定位；附未解决gap和覆盖范围。精确摘录及数值可机械核对；开放语义支持不能靠引用存在证明。必要时结果应为部分草稿或需复核，不冒充“全部符合”。

**安全边界**：结果正文只进受控产物，事件只记固定类别、ID、计数和摘要；`evidence_ref` 不接受任意模型自由字符串。人工审核沿用现有Gate设计，但要明确业务结果批准与工具执行批准不同；这一轮建议本身不会把两套Gate接起来。

**验收反例**：30→300；工作日/自然日混淆；甲乙方颠倒；否定词丢失；同一主题出现冲突；引用别的Run；引文不等于source切片；核心槽位为空；伪造JSON合法但业务不成立。已知可机械判定的错误必须拒绝成为完整结果；不可判定的语义结论保留未知/人工复核。

**收益/代价**：用户能看到缺什么，验收不再只看运行状态；代价是先限定领域、维护规则和标注集。先做这个，再谈泛化到完整合同或投研；本报告不提供法律/投资决策规则。

### B. P0：把检索进展接入DSH，不再等八轮才发现空转

**解决问题**：重复读取无收益、搜索前三项遗漏例外。

**接入点**：`dsh_runtime.py:151,209,232`；复用父子块与 `slot_progress/retrieval_control` 的思路，但需补运行状态映射，不直接调用helper就宣布完成。

**最小策略**：

1. 工具返回标明截断/还有更多命中；提供受限分页或按登记ID继续读取，并验证游标绑定文档与查询。不要把“前三个”称为全覆盖。
2. 对付款核对模板扫描候选段及相邻定义/例外，必要时扩展父块；总字数、读取数仍受限。字面词表不能保证发现所有隐含例外，覆盖不足应明确报gap。

4. 连续无新增后允许一次明确的查询/读取策略变化；仍无进展就输出未解决项并停止。预算耗尽、取消和权限拒绝始终优先，不以“还有gap”为由越限。

**不能机械复用的细节**：现有helper要求六维预算全部提供且任意维度为0即停（`adaptive_retrieval.py:163`）；DSH的 `max_cost_minor=0` 表示不批准额外余额付费，不是已经耗尽订阅Token，当前也未启用rerank。必须先设计适用维度/禁用状态的明确映射或契约演进，不能传六个假正数，也不能把禁用rerank当成整个Run耗尽。Token剩余来自持久账本并扣除预留，时间来自当前截止时间，不能由模型上报。

**验收**：第四条例外能被发现或明确未覆盖；连续同读不能耗到八轮才决定无进展；合法跨块读取不被误杀；同内容不同来源不能错误合并；取消和真实预算耗尽仍先停；禁止未准入semantic/api策略升级。

**工具部分**：统一两工具的注册描述、严格参数Schema、输出上限、资源范围、版本和只读属性。可发现集合与执行允许集合分别校验。加入固定错误类别；若允许一次参数纠正，要单独占用剩余预算，绝不重试未知是否已计费的请求。

**收益/代价**：解释每轮模型看到了什么、遗漏了什么；增加版本治理和兼容测试。先不用LLM压缩，避免新增未经预算的模型路径。上下文中的“已包含规则”仍不替代工具端授权。

### 数据与对照

建议第一版 **60个公开/合成案例：20开发、40留出**，按文档模板族分组隔离，避免同模板改几个词后同时进两侧。覆盖正常、无答案、例外在第4个及更后命中、跨块条件、表格、冲突/时间更新、提示注入和重复检索。冻结资料、问题、期望关键事实及人工rubric哈希；标注不进入检索、排序或模型请求。

### 指标口径

| 指标 | 判定方式 |
|---|---|
| 关键事实覆盖率 | 被正确回答且有有效来源支持的必需事实数 / 标注必需事实数；不能只数填了几个非空槽位 |
| 不支持的结论率 | 无可核实支持或与证据矛盾的原子结论 / 所有可核查结论；另报样本数和未知项 |
| 关键例外漏报率 | 需要提示但未呈现的例外 / 标注例外；与一般Recall分开 |
| Recall@K | 用独立问题检索，命中标注证据单元的数量 / 全部相关证据单元；固定证据单元避免不同Chunk大小占便宜 |
| 重复检索率 | 未带来新证据区间/来源的重复动作 / 总检索动作；与最终业务覆盖联合看 |
| 首个有用结果时间 | 从Run开始到首个可交付、通过该子目标验证的结果；不是第一token。当前只在最终发布有结果，基线计到发布，不能虚报中间可交付 |
| 完整结果时间与成本 | 端到端时长、主/辅助模型调用、Token、工具次数、重试/未知用量；真实费用按实际可得账单口径，不把套餐记成免费 |
| 保护性指标 | 越权、取消后发布、超预算发送、跨Run证据、正文进事件、临时目录遗留；现有安全回归必须保持 |

无答案案例单列“正确拒答/明确未知”，不把它的Recall分母0随意记成1。合成Provider只证明控制逻辑；真实模型效果需独立跑、逐案例记录，建议至少三次并按案例配对报告区间和失败分布。小样本或区间太宽时报告不确定，不能宣称显著更优。

### 建议发布门槛

- 固定安全反例零回归；已知可机械验证的错误不得被标为完整结果。
- 相对基线，关键事实质量不下降；若仅成本下降但例外漏报增加，不接受。
- 对“更好”的宣称，先冻结业务非劣容忍度、Token/延迟允许增幅，再比较；不要看完结果才改阈值。当前没有质量基线，故不提前编造提升百分比。
- 每个新增闸都有独立负例，并用去掉检查的定向突变证明能抓住对应错误；不是只让测试因别的异常失败。
- 必须保留“结构与引用通过≠语义正确≠人工批准”的用户说明。
