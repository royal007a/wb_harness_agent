# 第二十一批 MCP接口与执行权限

MCP统一工具发现和调用，不替代业务鉴权、幂等账本或发布审批。当前DSH只有平台登记的文档工具，没有对接外部业务系统的需要；应借鉴分层验证和显式接口，暂不引入MCP运行时，更不因接通协议就开放退款等外部动作。

## Client篇的可取之处与限制

M24 p1–6将系统适配、工具描述、模型选工具、平台执行、结果回送分开；p7–10按工具管理、绑定、聊天引擎逐步接入；p11–12强调多工具、安全权限和真实开发的迭代。可吸收的是协议适配器保持狭窄职责，先验证工具自身，再验证协议与完整业务链；不要为了统一工具接口再引入一套主循环。

- **标准化不消除系统适配和认证。** M×N到M+N是理想复用关系，不是实际维护量保证。业务API差异被移到Server，而不是消失；“只填地址、不处理认证”不能当接入条件。工具描述、参数和返回结构仍会变化，调用方要固定兼容契约。
- **工具发现不等于允许使用。** M24 p8描述绑定时检查Server启用，并按模型返回名称查工具，未给出每次执行时的主体授权、Run工具集合与Server身份绑定。多个Server同名、绑定后停用、模型请求未绑定工具，都应作为拒绝反例。模型给出的userId不能取代已认证主体。
- **解释的是循环，实施提示却只写两次请求。** p5承认连续工具轮次，p8仅列首次请求、一次工具执行、第二次流式回答；后续仍返回tool_calls时如何处理没有写全。不能从这个提示推出任意多轮或并行结果配对已成立。
- **只拼TextContent会丢失状态。** p7将结果转String、失败统一BizException，而M25明确使用isError。若适配时丢掉它，错误文本可能被当普通证据；非文本或结构化结果也要显式支持或拒绝，不能悄悄略过。状态码、稳定错误类别与面向模型的解释应分开。
- p6关于SDK资源泄漏及“每次新建再关闭”的建议没有固定issue和复现。本文不把它当已确认根因；连接是否真正关闭、建连费用、握手与取消时序，都应在选定SDK版本后测试，不能据此预设每次重建一定更安全或更快。

## Server篇的可取之处与限制

M25 p1–4从退款诉求拆出资格、提交、查询、撤销，p5–7分层实现与调试，p8–11做端到端对照并留下权限问题。查询和提交分离有价值，但平台必须持有最终执行许可，不能依靠工具description要求模型自律。

1. p3的提交工具只有orderId/reason，p6服务方法又要求userId/amount。应明确后两者由可信订单与认证上下文提供，而不是让模型补齐；金额、资格与当前订单状态在提交事务内重查，先前查询结果不是永久授权。
2. “查询没有进行中的退款，再插入”没有展示唯一约束或并发串行化；重复点击loading也不是去重。需要稳定业务身份、相同身份内容冲突拒绝，以及结果未知时的对账策略；不是失败后自动再退一次。
3. p5状态枚举没有撤销态，p6却要求撤销PENDING；查询承诺支持orderId/refundId，示例方法只有orderId。这些应先统一契约和迁移，而不是交给自然语言解释。statusLabel可辅助表达，不能覆盖程序状态或让模型擅自把预计天数说成工作日。
4. p7调试接口复用真实callTool，说明它也能造成业务副作用。调试权限、确认、审计和额度不能弱于正式路径；历史结果还要遵守数据留存与访问隔离，而不是默认保存任意正文。
5. p9验收直接从“我要退款”进入提交，没有展示额外确认。它不能证明p6description要求的用户确认已被执行层强制。更不能把资格查询、模型意图或工具发现等同于支付授权。

## 协议时代必须固定

课程p5–7使用旧HTTP+SSE端点。2025-11-25规范已经区分stdio和Streamable HTTP，并将旧HTTP+SSE列为兼容路径；所以“MCP Server就是独立HTTP应用”只适用于本讲架构，不是协议定义。[2025-11-25传输规范](https://modelcontextprotocol.io/specification/2025-11-25/basic/transports)

课程curl得到sessionId后直接tools/list，没有展示旧版本的initialize/initialized阶段；不能把这段当完整握手探针。这个要求只适用于相应旧版本。[2025-11-25生命周期](https://modelcontextprotocol.io/specification/2025-11-25/basic/lifecycle)

截至2026-10-07核对，官方2026-07-28版本公告已改为无状态核心、移除上述握手及协议会话。因此不能把旧握手要求写成所有MCP版本的永久规则。未来若接入，要同时固定SDK、协议版本和transport；本项目没有因此升级依赖或声称验证过新协议。[2026-07-28官方公告](https://blog.modelcontextprotocol.io/posts/2026-07-28/)

## 对当前DSH的取舍

| 已有接入点 | 本批可吸收的验收 | 当前不做 |
|---|---|---|
| dsh_provider.py:56，Run工具集合校验；dsh_runtime.py:319、326执行侧拒绝 | 模型要求未提供工具、错误类型、额外参数都应拒绝；Schema描述不代替执行校验 | 自动发现并执行任意远端工具 |
| dsh_crossings.py:94–140，Run/代次/轮次票据与内容摘要 | 同票据只回放原响应，不重复计数；取消后拒绝；结果未知不重发 | 把协议request id直接当跨Run幂等身份 |
| dsh-adapter/controlled.patch.yml:27关闭mcp-resources | 核对配置之外的实际工具集合，不把“插件没开”当唯一边界 | 外部Server、退款、文件系统和shell权限 |
| HA86初始化分层、HA89和HA91故障阶段探针 | 连接可用、模型已发送、工具已执行、业务已提交分别验证 | 用端点200或有SSE流代表业务验收完成 |

未来确需MCP时，先做只读、固定工具、合成数据的协议适配切片；补鉴权主体、目标地址策略、工具版本冻结、错误保真、取消与未知结果的反例。收益是复用外部工具生态，代价是新增网络信任边界和协议生命周期；当前文档核对工具无需为此重构。
