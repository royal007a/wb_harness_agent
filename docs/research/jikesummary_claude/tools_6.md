## (1) 各讲要点与排雷方法

**02 六大契约**
- 要点：
  - 工具要拆成原子操作，权限挂在工具名上。
  - 描述写六要素（做什么、何时用、和谁不同、参数、约束、示例）。
  - 每个工具声明元数据：副作用级别、是否只读、是否强制幂等。
  - 幂等键由 Loop 按 `run:turn:index` 注入，不让模型生成。
  - 报错分红绿灯：红灯别重试，黄灯退避重试，并附 hint；返回结果要分页且限大小。
- 排雷：查日志里“同一参数被反复调用的次数”和“单次返回字节数”。错误码不带 hint 的，一律当缺陷处理。

**03 注意力稀释**
- 要点：
  - 一次推理里模型能看到的工具不超过 20 个；超过 20 个按 L1/L2/L3 分层懒加载，超过 50 个要上检索。
  - 冷门工具的检索按工具名、描述、领域三个维度加权打分，不用向量。
  - 描述先写“何时用”和“和谁互斥”。
  - 每个工具单独熔断（closed/open/half_open）。
  - 动态追加的工具放在数组尾部，保护前缀缓存。
- 排雷：把描述相似的工具两两列出来，查边界有没有写“互斥”；用 `tool_health` 看哪个工具在反复抖动。

**07 容错 Edit**
- 要点：
  - 匹配分四级降级：精确、换行归一、首尾裁剪、逐行去缩进。
  - 安全底线是唯一性：匹配到多处就拒绝替换。
  - 报错原样回给模型，让它自己纠错。
- 排雷：先统计 `not found` 的失败里，有多少只是空白或格式差异造成的。

**08 并发**
- 要点：
  - 同一轮里的多个调用默认互相独立，按 Fork-Join 并行执行。
  - 结果用预分配切片保持原顺序。
  - 同时有读有写时有竞争风险（含先读后改的 TOCTOU），所以“只读并发、涉写串行”。
  - 用信号量限制并发数。
- 排雷：检查同一批调用里有没有写操作，或者同一路径出现两次。

**09 TAO 选错工具**
- 要点：
  - Action 按完整的业务步骤划分，尽量正交。
  - 描述要写适用场景和不适用场景；参数和返回值都越少越好。
  - 只允许从本轮候选里选，用代码校验，不能只看工具是否存在。
  - 前置条件放在代码里检查；要求模型输出选择理由和证据；可配正反 few-shot。
- 排雷：抽查“选错工具”的 case，看是边界模糊还是候选太多。

**09 工具管理**
- 要点：
  - 工具面向 Agent 设计；命名要能被发现（例如 `crm_customer_search`）。
  - 返回值要翻译成自然语言含义。
  - 常用工具全量加载，其余渐进披露。
  - 参考 Claude Code 的 5 层权限（hook 拦截、禁止名单、安全模式、白名单、工具自身属性），以及 Auto Mode 的熔断回退。
- 排雷：建一套自然语言指令评测集，测工具召回率。

## (3) 最优先的 3 项优化

1. **P1：可纠正的输入错误改为软失败。** 只针对 `CLAUSE_NOT_FOUND` 和查询长度/为空，返回带 hint 的结果，越权仍然 fail-closed。要求过突变测试和对抗测试。
2. **P1：`search_document` 做空白和 NFKC 归一化。** 在评测集上对比零命中率和工具调用次数。
3. **P2：补“何时用 / 互斥”描述和零命中 hint。** 用真实豆包跑评测集，对比 search/read 的调用比例和 `DSH_NO_PROGRESS` 的出现率。

## 两件不要做的事

- **不要上 L1/L2/L3 分层、工具检索或单工具熔断。** 现在只有 3 个工具，离 20 个的阈值很远。熔断反而会削弱现在的 fail-closed 语义。
- **不要把工具改成并行，也不要引入自动重试。** 工具都是内存操作，并行没有收益。串行加票据回放是 HA-0083 的正确性基础；自动重试也违背“未知用量冻结、不重发”的账本契约。
