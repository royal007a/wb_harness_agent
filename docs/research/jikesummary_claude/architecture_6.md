## 1. 各讲要点与排雷方法

**03《01 操控循环》（徐昊）**
- 有两层循环。外层是 PDCA，负责拆分任务、跟踪进度，每一步验收通过才进入下一步。内层是操控循环：前馈 → 行动 → 反馈 → 调整。
- 前馈和反馈缺一不可。只有反馈，Agent 会重复犯同一个错；只有前馈，Agent 会草草收尾。
- 上下文清楚的子任务不必再拆，重点是交代清楚、加好约束。
- 排雷方法：把指令逐条标注为"前馈"或"反馈"。没有对应反馈检查的规则视为不受控。

**04《02 四个子系统》**
- 内置 Harness 就是"推理-行动-观察-自我纠正"这个循环。
- 控制分两类。推断型控制靠模型判断，结果不确定；计算型控制交给工具或代码，结果确定。数字数、HTTP 状态码这类检查不要交给模型。
- 四个子系统：指令、工具/技能、环境、状态。环境要可复现，否则反馈不可信；状态是前馈和反馈之间的桥梁。
- 排雷方法：每条检查先问"能不能写成代码"。能写成代码的却交给模型判断，就是缺陷。

**08《Loop Engineering》（黄佳）**
- 区分执行型和内容型 Agent。执行型 Agent 会出现跳步、参数漂移、虚假成功、死循环。
- 叙事平面与控制平面要分开。确定性参数由程序掌控，并且要有可追溯的来源。
- 边界和停止条件是循环本身的一部分；验证必须来自循环外部，不能自己给自己打分。
- 用户中途换意图时，当作一次受控中断处理。
- 排雷方法：逐个列出关键参数，问"它从哪来、谁写的"。

**17《15 pimono 起点》（邢云阳）**
- 四层分层：pi-ai、pi-agent-core、pi-coding-agent、pi-tui。好处是可审计、可替换。
- 事件驱动：turn 和 tool_execution_start/end 事件是审计和拦截的统一切入点。
- 统一的 Model 抽象，可按成本切换模型。
- 排雷方法：出问题时按层定位（模型调用、循环逻辑、业务封装、界面）。

**24《21 行动模块导论》**
- 工具返回 success 不等于行动正确。正确行动要同时满足六项：目标一致、范围授权、状态新鲜、策略准入、副作用只发生一次、证据完整。
- 四本账：状态账、动作账、效果账、证据账。只看终态会漏掉重复执行。
- 两条原则：最小权限，以及每次调用都要检查（完全仲裁）。另外要有 ActionEvent 记录，并区分"结果未知"这个状态。
- 排雷方法：做消融实验。固定目标和注入内容，一层层加防线，看每层挡住了什么。

**29《26 反思模块导论》**
- 反思契约：反思谁、回到哪个目标、拿什么对照、允许改什么、改完怎样验收、何时停止。
- 外加验证器治理（ValidatorPolicy）：检查器本身也要有负责人、校准、回归测试和有效期。
- 没有新证据的自评只能查出"自洽"，查不出"真实"。课上例子：看不到账本的自评打了 96 分；加严提示词也只降到 88 分，盲区不变。
- 发现偏差不等于知道原因，不要编造根因。
- 上线后要盯的指标：轨迹与终态分歧率、错误放行率、越权改变率、无进展循环率。
- 排雷方法：问"第二遍检查到底多拿到了什么新信息"。

## 3. 建议优先做的 3 项
1. **补语义极性校验（P0）。** 平台目前对否定词有盲区（dsh_findings.py:239），这是错误放行的主要风险。修完后跑突变测试，确认能抓住漏掉的否定词。
2. **工具输入错误改为可纠正的观察（P1）。** 目前模型一次幻觉出的 clause_id 就会让整个 Run 失败，浪费真实豆包额度。做法是把错误作为观察返回给模型，用现有的无进展规则兜底。
3. **把评测集变成"镜子校准"（P1）。** 用 dsh_payment 评测集产出两个数：词表召回率和错误放行率，纳入 verify.sh 门禁。

## 不要做的 2 件事
1. **不要加"同一个模型再自评/反思一遍"的 LLM 层。** 第 26 讲已经演示过：没有新证据的自评只能查出自洽。现有的机械校验加人工复核才是对的路线。
2. **不要为了追 pimono 去加模型降级或自动续跑。** 代码里 allow_fallback 是 False（:111），并写明"不会回退"（:84），重启后也不自动续跑（:548）。在 A2 检查点证据做出来之前，自动重试会破坏"副作用只发生一次"和账本冻结。

第 2 条做法写的是"返回观察并计数"。我没读完 dsh_crossings.py 第 134 行之后对异常的处理，实施前要确认：票据在 in_flight 状态下出错后，回到模型时会不会被判为不可重放。
