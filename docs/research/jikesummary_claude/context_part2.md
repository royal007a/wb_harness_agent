# 上下文工程 课程摘要（第 17 个文件起，共 15 讲）与 HarnessAgent DSH 对照

> 输入：`上下文工程/` 目录下按 `ls | sort` 排序后跳过前 16 个的 15 个 .txt。项目代码核对基于 `~/code/ai/harnessagent-dsh`（只读），行号为本次读取时的值。

## 一、逐讲摘要

### 12-11｜会话管理：Session 物理隔离与 Working Memory 的底层实现（Tony Bai《从 0 开始构建 Agent Harness》第 12 讲）
- 核心观点
  1. 多端并发（飞书群 A/B、微信用户）必须由 SessionManager 按来源 ID 分配独立 Session，每个 Session 自带历史队列和读写锁；全局单个 contextHistory 会让不相关任务串在一起。
  2. Session 是长期历史池；真正发给模型的是"System Prompt + 最近 N 条"的 Working Memory（示例 N=6，正文称 6–10 条足够）。
  3. 截断边界防线：如果截出来的第一条是"孤儿" ToolResult（它对应的 ToolCall 被截掉了），必须丢弃，否则 API 返回 400。
  4. 生产级做法是 Token 感知截断（从后往前装到安全水位）和摘要接力（用便宜模型把被截掉的历史压成百字大纲，放进 System Prompt 头部）。
  5. 只按条数截断不限制单条消息的体积：一次 read_file 读进 5MB JSON 就能撑爆上下文，所以下一讲要引入压缩。
  6. Registry/WorkDir 一般全局唯一；如果真要多工作区，必须通过 ctx 把 Session 的 WorkDir 传给工具，不能在构造时写死。
- 排雷/定位方法：用"先读密钥、再塞 6 轮闲聊、再追问"的脚本验证截断是否真的生效；用两个并发 Session 互相询问来验证隔离。评论区补充：条数和字符两个维度先到先停，至少保留最后一条，避免返回空记忆后死循环；同时保留最初的用户需求。
- 关键规则："如果切片首条属于“孤儿”工具响应，我们必须将其强行舍弃，顺延到下一条正常的 User/Assistant 消息。"

### 19-17｜进阶：长上下文与 Skill 调用构建大合同审查流水线（邢云阳《Harness Agent 脚手架实战课》第 19 讲）★与本项目直接相关
- 核心观点
  1. "Skill 管业务，代码管工程"：6 类风险定义、审查步骤、输出格式、评分规则、典型案例都放进 Skill（SKILL.md + references/）；代码只负责解析、切块、调用 Skill、聚合。业务规则变了只改 Skill。
  2. Skill 的 description 要写具体的触发场景；输出分两种模式：markdown 报告给人看，JSON 数组（level/type/clause/originalText/suggestion）给程序聚合，代码调用时必须明确要求 JSON 模式。
  3. references 按需读，不一次性塞满上下文；Skill 要引导模型做语义理解，不要只做关键词匹配。
  4. Skill 本身解决不了上下文长度问题。80 页合同要按章节/条款边界切块（正则 `第[一二…十]+章|\d+\.\s|第\d+条`），不能把一个条款拦腰截断，否则看不到违约责任失衡这类对比关系；相邻的小条款合并，接近 maxChars=6000 时再切。
  5. 每块调用一次 Skill，然后合并 JSON；总评 A/B/C/D 由确定性代码计算（high≥3 或 high+medium≥8 → D；high≥1 或 medium≥4 → C；medium≥1 → B）。
  6. Token 自适应：当前上下文估算超过窗口的 70% 时，把块大小减半（3000），仍然紧张就 compact。
- 排雷/定位方法：思考题和评论区指出，按标题切块仍然有跨分片问题：条款之间互相引用、组合风险难发现、长上下文注意力衰减、压缩后丢失原始细节。单条款识别效果好；组合风险要在全部读完后再做一轮全局复盘兜底。
- 关键数字/规则："当上下文超过窗口 70% 时，就把块大小减半，给 Skill 指令和输出留足空间。"

### 13-10｜多模态融合：日志、SQL 和 PDF 一起进 Agent（黄佳《Agent 设计模式之美》第 13 讲）
- 核心观点
  1. 根因往往是"数据形态不对"，不是 prompt 或模型不行。整份 PDF 直接喂进去会看错图（把 5800 亿读成 5800 万）；全部转成文本又会丢掉空间关系。
  2. 决策规则：空间关系本身就是信号的保留为图；否则转成紧凑、可检索的文本或结构（Markdown/JSON/Mermaid）。合同条款属于"转结构化文本"这一类。
  3. 融合器（fuser）要做三件事：识别形态、按形态分发、为每次处理记录 trace（FusionEvent：形态、tokens_out、耗时、方法）。没有 trace 就是黑盒。
  4. PDF 默认取 TOC、关键页和业务 hint，不整份塞进去；长日志走 bash 预过滤 → 低成本 Sub-Agent → 结构化摘要；数字核查必须给出 page/chart 引用，找不到引用就标 confidence=low。
  5. 同一份文档会被多次问答，应优先接入 prompt caching 或批处理；非核心的重依赖（cv2/pdfplumber 等）用 lazy import 或 try-except 降级，避免在 headless 环境启动时崩溃。
  6. Sub-Agent 启动前必须声明 token、时间、递归三类预算，任一触发立即停止；关键结论放进状态存储，上下文里只传指针。
- 排雷/定位方法：按形态统计 token 占比，健康区间为 text 40–60%、image 10–30%、structured 10–20%、log 摘要 5–15%；fusion p99 < 5s；bash 过滤压缩比在 0.01–0.05 之间健康，>0.1 说明过滤太松，<0.005 说明过滤太狠。图表题用"直接看图答 vs 原始数据"的 10 题对照来定位错误出在读数、坐标轴、图例还是单位。评论区作者回复：找关键页先用零 LLM 的结构信号，再用每页 30–50 token 的廉价指纹排序，最后按 query 检索，只对选中页取全文；并非所有 Agent 都需要这套复杂流程（奥卡姆剃刀）。
- 关键规则："让视觉模型帮你看图，结构化数据负责算数。"

### 13-11｜指令文件腐化：AGENTS.md 越来越长，Agent 反而变笨了（徐昊《Agent 驾驭工程之美》第 13 讲）
- 核心观点
  1. 腐化的本质是"只增不减"：每条规则加进去时都有效，但累积以后会出现优先级冲突和矛盾（"尽快""适当""必要时"在不同规则里指向相反行为），重点也会被淹没。
  2. 模型对长文本中段利用率低（Lost in the Middle），写在中部的安全约束最容易失效。
  3. 治理方法是分层：入口文件只做说明，细节放进原则文档或 ADR，按需读取；简单场景用规则登记表（编号/内容/来源/优先级/适用条件/过期条件/状态）。
  4. 维护三件事：确定优先级（裁决和清理的基础）、检测矛盾（只检查适用条件重叠的规则对，按优先级裁决，裁决不了的交给人）、定期清理（没有过期条件的规则永远删不掉；删除要留痕，标为 deprecated）。
  5. 矛盾检测可以做成 skill 或定时任务，作为固定动作执行。
- 排雷/定位信号：指令里频繁出现"但是""除非"之类的例外条款；Agent 偏离预期时，对着规则列表也指不出根源。判断依据不是行数，"50 到 200 行的指令文件都是健康的"。

### 13-12｜上下文窗口：怎么设计一个动态编排的 Context 策略？（邓明《AI Agent 系统设计面试现场》第 13 讲）
- 核心观点
  1. Context Compiler 的抽象是 `Window_t = Inject(Order(Compress(Select(AllContext_t, TaskState_t), TokenBudget_t)))`。窗口是经过选择、压缩、排序、注入四步得到的产物，不是简单拼接。
  2. Select 有三种方式：强规则（模板占位或代码写死，作者实践中最喜欢）、检索召回、模型筛选（多一次调用，成本高、少用）。每个步骤需要的上下文不同，"弱水三千，只取一瓢"。
  3. Compress 是动态的，由重要性、剩余窗口和调用目标共同决定；可以预先保存多个精度版本 L0–L4，按需加载。
  4. Order：越重要越靠前。参考顺序为 System/Spec → Goal → 硬约束 → 任务状态/Plan → 已确认事实 → 当前 Evidence → 工具 Observation → ……；同时兼顾 Prefix Cache，把不常变的内容放前面。常见错误是硬约束没有从用户输入里提出来，排在后面被淹没。
  5. 按剩余窗口分档：Full [80,100]、Balanced [20,80)、Compact [5,20)、Minimal [0,5)。进入 Minimal 视为不健康，需要单独监控。最新用户输入、硬约束、已确认事实、Plan 状态始终原样保留。压缩内容要附兜底条款"可召回更详细内容"，并提供召回 Action，但窗口真满了时召回也放不进去。
  6. 其他因素：任务风险等级、信息可恢复性（工具输出没有落库的就无法召回，不能只放索引）、可信度排序（用户确认 > 权威工具结果 > 原始文档 > 历史摘要 > 模型推测）。工具描述压缩会严重影响工具选择准确率，要慎用。
- 排雷/定位方法：作者承认"在实践中，这种非常动态的策略性价比就不那么高了"，最佳办法是换大窗口模型。评论区建议用字符数估 token，按 token = a × 字符数自行标定系数 a。
- 关键规则："高风险任务就应该尽量使用大窗口的模型，避免压缩之类的信息损耗引发问题。"

### 13-12｜突破内存：基于阶梯降级的 Context Compaction 策略（Tony Bai《从 0 开始构建 Agent Harness》第 13 讲）
- 核心观点
  1. 条数窗口挡不住单条大结果（一次读进 1MB 日志就是 400 context length exceeded）。防 OOM 的优先级高于记忆完整性。
  2. 不能直接删除工具结果消息：ToolCall 还在而结果没了，模型会以为调用没发出去，于是重复调用并原地打转。要"丢弃冗余数据，死死保住意图和逻辑链"。
  3. 两级降级：远期历史的工具结果超过 200 字的整体掩码（只注明原始长度），远期 assistant 长推理折叠；Working Memory 内的单条结果超过 1000 字的掐头去尾（各留 500）；System Prompt 和 ToolCalls 永远不动。
  4. Session 里保存全量原始数据，Compact 只作用于本轮发出去的临时上下文。
  5. 局限：掐头去尾可能恰好丢掉中间的关键堆栈；远期掩码会迫使模型重读。替代方案有 LLM 摘要（成本高，可能漏信息，应异步执行，不放在每次请求前）、Memory Paging（向量库 + search_memory 换入）、长上下文模型。
- 排雷/定位方法：用 `yes ... | head -n 2000` 造一个大文件，端到端诱发超限，观察压缩前后的字符数日志；作者在评论区同时强调纯逻辑组件必须写单元测试。评论区指出的盲点：远期 write_file 这类 ToolCall 的 **arguments** 本身也可能很长，同样需要掩码，只保留意图骨架。思考题：用每次 Response 的 Usage.PromptTokens 把固定字符阈值改造成自适应水位。
- 关键数字：字符估算"英文 1 token ≈ 4 字符；中文 1 token ≈ 1.5 字符"；掐头去尾 500+500；作者引用 Lost in the Middle（arXiv 2307.03172）作为掐头去尾的依据，并把 Anthropic Context Editing 的 clear_tool_uses 列为远期掩码的业界实践。

### 14-11｜记忆模块导论：从草稿纸到长期记忆，建立 Agent 的经验沉淀秩序（黄佳《Agent 设计模式之美》第 14 讲）
- 核心观点
  1. 记忆要解决的是长程任务在时间中的漂移，不是"记住东西"。要记住的是承重信息：关键判断、依赖路径、失败方案、禁止动作、未完成假设、下一步边界。
  2. 反例：进度只写"已完成/待继续"，丢掉了循环依赖路径和"不要先移动 UserSession"这条禁令；"待继续"那一行还把下一轮往危险方向推了一把，结果 CI 改坏、项目回滚。
  3. 生命周期：context window → scratchpad → structured trace → long-term memory → retrieval/replay/forgetting。不要把 raw chain-of-thought 当业务记忆，企业要的是可验证、可审计、能续接的判断。
  4. 四种模式"架、取、录、省"：分层保留、RAG、进度追踪、失败日记；程序性记忆放到 Skill Package 讲。
  5. 选型：不要同时上两套记忆系统（单一事实来源）；结构化记忆放文件系统，非结构化大库放向量库或图库；健康的中间态是"Agent 提议、框架定规矩"（schema 约束 + trace 验证有没有被用上）。
  6. 安全：记忆注入、投毒、篡改。写入什么、谁有权改、什么时候过期都需要设计。
- 排雷/定位方法：Memory Trace 定位链 should_write → write → retrieve → use → avoid_repeat_failure。没写入是沉淀问题，没取回是检索问题，取回不用是推理/规划问题，用了还错是质量或适用边界问题。实验：同一长任务分别给完整结构化记忆和一行摘要，比较成功率。
- 关键规则：作者回复中的三问——"保存多久、由谁读取、怎样影响下一轮行动"；"经验要经过验证后才能影响未来任务"。

### 14-13｜摘要/压缩之后，你怎么把细节找回来？（邓明《AI Agent 系统设计面试现场》第 14 讲）
- 核心观点
  1. 摘要和细节召回是一对双生子。摘要不是"一段话"，而是多字段结构：整体摘要（按意图分区、长期保存、不归档）、章节摘要（每 20 轮一章，整体摘要 + 最近 2–3 章）、大模型输出摘要、关键事实、中间结果。
  2. 关键事实的定义是"会影响后续决策、工具调用、上下文组织、最终输出、约束校验的信息"，分六类：目标、硬约束、软偏好、用户确认（含否认）、决策（含理由）、实体。要结构化保存，并能回溯到原始来源。
  3. 值得召回的细节只有影响当前决策的：影响目标、约束、路径选择（方案 A 失败过就不能再用）、工具调用（某工具失败过）、最终表达。
  4. 召回的工程原则："当前 K 轮原文保留，K 轮之前走检索"，用来规避同步延迟；冲突裁决有两个套路：last win 和权威优先，同时要区分"冲突"和"细化/强化"。
  5. "只要上下文窗口有限，细节就不可能做到 100% 不丢"，目标是保住会影响决策的细节。
  6. 模型可读摘要：删除寒暄和填充词，保留目标、实体、数字、约束、否认、证据来源；"不能/不要/必须/不超过/可能"绝不能删；不得把不确定改成确定，不得把建议改成已执行，不得把 Assistant 推测改成用户确认。迭代式召回：只给索引，模型判断缺什么再用 Action 召回；要设最大迭代次数，窗口真放不下就报错。作者原话"这个方案实践慎用，面试大胆用"。
- 排雷/定位方法：异步摘要需要时可能还没生成，需要等待（轮询或 WaitGroup）；评论区两条都批评本讲理论多、缺伪代码。
- 关键规则："当轮对话的细节不走召回，当轮对话之前，数据就已经完成同步了。"

### 14-13｜记忆沉淀：状态外部化，基于文件系统的持久化记忆与待办管理（Tony Bai《从 0 开始构建 Agent Harness》第 14 讲）
- 核心观点
  1. 压缩会让长程任务失忆，进程被杀后内存 Session 也会清零。这一讲的方案是状态外部化：让 Agent 用 read/write/edit_file 维护 PLAN.md（全局设计与约束）和 TODO.md（checkbox 进度），而不是在内存里维护黑盒状态机。
  2. 好处：透明可观测、零成本 HITL（人改文件就能纠偏）、跨进程断点续传、省上下文（需要时 read_file 一次即可）。
  3. Plan Mode 作为开关：只有复杂任务才注入重型规范，避免简单命令也走"官僚"流程。
  4. Plan Mode（宏观导航）不能替代逐轮慢思考（微观纠偏）；建议动态分配算力，在目标变化或工具返回非预期结果时才开启慢思考。
  5. 多层记忆：Working Memory → 任务状态（PLAN/TODO，任务结束后归档）→ 情景日志（按日期 md + MEMORY.md，压缩前用静默轮次把未落盘信息写进去）→ 混合检索（向量 + BM25，BM25 用于精确匹配 ID、错误串）。
- 排雷/定位方法
  - 隐蔽坑：严格的 OpenAI 兼容端点要求带 tool_calls 的 assistant 消息即使 content 为空也必须显式传 `""`，否则返回 400（智谱 code 1214）。
  - `./server &` 经 os/exec 执行时，没有分离 stdio 会让父进程卡死，模型不知道自己不在交互式终端里，容易形成 Doom Loop。
  - 评论区：模型会变成"打勾机器"，不再写进展推理，解决办法是在 ToolResult 末尾拼接系统提醒；旧 PLAN/TODO 全部打勾后，由引擎代码负责归档，不交给模型判断；不要让模型用 sed 改 checkbox（`[ ]` 会被当成字符类）；条数截断可能把最初的用户任务截掉（"No user query found"）。作者回复：能用代码定死的流程约束最强。
- 关键规则："只要 TODO.md 还在工作区里，你重新启动程序……它读取文件后就能无缝恢复进度。"

### 15-12｜分层保留：给 Agent 的记忆建一套货架（黄佳《Agent 设计模式之美》第 15 讲）
- 核心观点
  1. 分层的依据不是冷热，而是五个坐标：作用域、生命周期、权威来源（人、工具、框架、模型推断）、证据、上下文预算。长程 Agent 出问题，常常是因为不同可信度的信息被放在了同一层。
  2. 五层货架：Policy/Managed（红线，不可被覆盖）→ Project/Domain（进仓库、可 review）→ User/Tenant（schema 化，不写散文）→ Task/Session（checkpoint）→ Scratchpad/Turn（TTL 短、用完即丢）。层数要和产品的作用域一致。
  3. 覆盖规则比层数更重要："内层可以临时影响外层的使用，但不能自动改写外层的事实。"升层需要证据：scratchpad 只能提出候选，越长期、越权威的层，写入门槛越高；POLICY/PROJECT 不允许 Agent 直接写。
  4. 每层有自己的 backend、TTL、token 预算、加载、写入和淘汰规则；assemble_context 按层分预算组装，不按时间。
  5. 长期层的条目必须带 value/source/confidence/evidence/set_at/scope/schema_version；高风险场景下关键状态要实时写回，不能等 session 结束。
  6. 本质是工作集（working set）管理：好的分层不看存了多少，而看该进的进了、不该进的挡住了。
- 排雷/定位清单：四种失败模式——全量历史塞进 prompt、长期记忆写成自由文本、scratchpad 直通长期层、没有降权或失效机制（"旧记忆就会变成新判断的毒药"）。反例：一次"想看便宜的"被写成长期偏好；一次 debug 用的 mock 地址被写进项目规则。评论区答 K8s 落地：持久存储是主副本，本地文件只是工作副本，要处理重试和写回冲突。

### 15-14｜为 AI 股票分析工具装上 Agent（四）：记忆管理（产品二姐《AGI 产品经理全栈进化指南》第 15 讲）
- 核心观点
  1. 开放 memory 工具的前提是多用户记忆隔离，没做隔离之前这类工具应该默认禁用。
  2. 拆解任何记忆系统都可以用五个维度：What（有哪些记忆）、Where（存在哪）、When（何时写入，如会话结束提取或"梦"中提取）、How（如何使用，如渐进式披露：先给描述和文件名，再取具体内容）、是否支持用户隔离。
  3. Hermes 的三层：SOUL.md（开发者写的人格，每次注入）、USER.md/MEMORY.md（Agent 自己写）、外部 Provider（可选）；Open WebUI 的记忆由用户手动添加，每次按语义取最相近的 3 条。
  4. 隔离做法：用 OpenAI 规范中的 `user` 字段（或 X-Hermes-User-Id）把用户 UUID 映射到 profiles/<uuid>/ 目录，所有读写都指向该目录。
  5. 业务化：替换默认 SOUL（"数据优先：先调工具拿数据……绝不凭空捏造价格或财务数字"），在提取引导里追加业务字段；由浅入深按需迭代，记忆量大了再引入渐进式披露。
- 排雷/定位方法：用两个账号分别让 Agent 记住相反的偏好，再检查 profiles 下是否生成了两个独立目录、内容是否互不串扰。评论区三条都反映本讲难以实操、源码不清楚，可借鉴的工程细节有限。

### 16-13｜检索增强：Agent 的知识库和证据链（黄佳《Agent 设计模式之美》第 16 讲）
- 核心观点
  1. RAG 的目标要从"相似文本召回"升级为"可用、可信、可追溯的证据取回"。生产级 RAG 的重点在写入侧：知识源登记、解析、切块、索引版本、权限。
  2. 两个平面要分开：机械真值（id、金额、批次号）由 SessionState 或工具绑定，并带 provenance；业务证据（规则、口径）才交给 RAG。LLM 从召回文字里"读"金额或 id 是执行型 Agent 最常见的事故源，所以结构化状态应该直接查业务系统。
  3. 失败通常是多个环节叠加：知识源没治理（过期、矛盾、没 owner）、切块切坏（条款、表格被硬切，看不出属于哪一章哪一条）、metadata 太薄、只靠 embedding 漏掉条款号或错误码（需要 BM25 混合）、没有引用链。
  4. 索引是可发布的软件资产：先登记源（doc_id/owner/effective/hash/status），再做可复现切块（chunk_id = hash(doc_id+parser_version+chunker_version+chunk_index+text_hash)），写 manifest，建候选索引并跑 golden questions，通过后用 alias 做蓝绿切换，同时准备退休、回滚和备份。
  5. Contextual Retrieval：在每个 chunk 前补一段上下文（哪份合同、哪一节、什么适用期）。Anthropic 报告 top-20 检索失败率从 5.7% 降到 3.7%，加 BM25 后降到 2.9%，再加 reranker 降到 1.9%。特别适合条款、合同、法规；材料短且独立时收益有限，应先做 A/B。
  6. 证据契约四件套：source / version / scope / citation（页码、章节、条款号、chunk_id、source_hash、index_version）；`is_usable_on`：召回到不等于能用。
- 排雷/定位方法：RetrievalTrace 记录请求、索引版本、候选、重排、实际使用和 missing_reason，把错误分成四类：没召回到（召回问题）、被重排压下去（重排问题）、用了过期材料（知识源问题）、材料对但没采纳（推理问题）。抽 50 条真实问题，人工检查材料入库后的形态（表格行列、页码、条款号能否追溯）；"答不上来，先别急着调 top-K"。
- 关键规则："相关性是给人看的排序，证据是给机器用的依据。"

### 17-16｜对话/任务特别长长长……怎么办？（邓明《AI Agent 系统设计面试现场》第 17 讲）
- 核心观点
  1. 结论是"长任务问题，本质上就是上下文管理问题"：信息多、依赖复杂，早期一个不起眼的判断可能是后面十几步的前提。
  2. 六类漂移：目标漂移、约束漂移（擅自补上"千万级用户"）、状态漂移（工具返回失败却标成成功）、证据漂移（拿旧文档下结论）、细节丢失（"绝对不能改"被摘要成"尽量少改"）、错误累积（把累计用户当成日活，后续全部基于错误数据推演）。
  3. 基础方案：Plan 模式在阶段结束、关键产物生成、高风险工具调用、被大量依赖的节点之后设置 Checkpoint（检查目标、约束、状态、证据，决定 Retry/Rollback/Replan），不要每步都设；ReAct 每轮重新回答"我还差什么"，不只总结"我得到了什么"。
  4. 高级方案：(a) 独立的 Context Verifier 做漂移体检，在阶段结束、上下文占用到阈值、Replan 前后或出现异常信号时触发，输出漂移类型、影响范围和修复建议，不整单重跑；(b) 事件溯源 + 可信快照：状态 = 最近快照 + 后续事件，出问题时回到可信快照，只重跑受影响的步骤，同时能定位是哪次更新引入的错误；(c) 分阶段执行 + 结构化交接（总目标、已完成、已确认事实、有效硬约束、证据索引、未解决问题、下阶段输入），这一条违背单 Agent 优先原则，要慎用。
  5. 目标不是永不出错，而是更早发现、更准确定位、从中间可信状态恢复。
- 关键规则："Checkpoint 不能保证 Agent 永远不出错，但可以阻止一个小错误被后续几十个步骤不断放大。"（评论区批评本讲缺少具体场景。）

### 18-15｜失败日记：让 Agent 把摔过的跤变成本事（黄佳《Agent 设计模式之美》第 18 讲）
- 核心观点
  1. 失败日记不同于错误日志、Retry 或 Postmortem：它服务"下一次 Agent"，记录失败模式、根因、教训和召回条件，并主动进入下一次任务。闭环为：检测 → 分类 → 证据与根因 → 审查 → 相似任务召回 → 改变行动 → 观察是否复发。
  2. 失败边界分四类：hard_failure、gate_failure、semantic_failure（表面完成但目标错了）、safety_failure。偶发抖动不进日记，标准是"是否值得改变下一次行为"。
  3. 六层结构：边界、分类（约 8–12 类，如 mechanical_state_mismatch、context_contamination、hitl_bypass）、证据包（三平面快照 + 原始观测）、根因与补救（禁止写"模型幻觉"这类无法指导改进的根因）、召回触发器（task_family + tool + mechanical_keys，比 embedding 可靠）、留存与审查（draft → needs_review → approved → archived，只有 approved 才召回）。
  4. 召回点：新任务启动、规划时、高风险工具调用前（这一点最有价值，"短危险卡"胜过十条长日志）。高风险类别不自动淘汰，还要转成永久回归测试。
  5. 失败日记本身是攻击面（记忆投毒、MemoryGraft；OWASP 把 Memory Poisoning 列为头号关注）。写入端要有来源、人审、租户隔离；召回到的经验只当"边界提醒"，不当 ground truth。
- 排雷/定位指标：重复失败率（核心）、召回有效率、漏召回率、误提醒率。落地第一步是把 Verification Gate 的 gate_failure/safety_failure 自动转成日记草稿。
- 评论区要点（作者认可）："确定且高频的下沉为校验、权限或 DAG；依赖情境的沉淀为 Skill"，失败日记的价值在于推动系统改变，而不是积攒补丁。反例：接口超时后模型写下"永远不要调用 A 接口"，这类不合理记忆需要人工审计。

### 18-17｜如何设计一个面试中富有竞争力的上下文管理机制？（邓明《AI Agent 系统设计面试现场》第 18 讲）
- 核心观点
  1. 上下文管理要回答的完整问题是："什么内容，应该在什么时间，以什么形式、什么粒度和什么顺序，进入当前的大模型窗口？"
  2. 基础方案围绕五问展开：有什么（不只聊天记录，还包括用户、任务、约束、知识、工具结果、运行状态）、怎么存（按结构和生命周期选存储；存储层不等于窗口）、怎么找（对查询做封装，不直接给通用 SQL 执行器；检索不只是"向量化后 Top-K"）、怎么压缩（不一刀切，目标、硬约束、任务状态、关键证据独立维护，不依赖对话摘要）、怎么召回（被压缩的内容保留原文和索引）。
  3. 高级方案：围绕一个具体业务难题组合两三个机制，避免堆砌名词；例子是"稳定偏好 vs 临时变化 vs 压缩丢细节"，冲突时先召回原始证据，仍不确定就向用户澄清，不直接覆盖。
- 本讲属于前几讲的汇总和面试话术，新增工程信息不多。

## 三、最值得做的 5 项优化

1. **【P0】让 HEADING 识别中文数字条号"第十二条"，并补充评测**（`backend/adaptive_retrieval.py:9`）。这正是 19-17 讲的核心要求"不能把一个条款拦腰截断"，已实跑确认是缺口，而且现有 126 个条号全部是阿拉伯数字，评测完全没有覆盖。验收标准：单测断言每块以条号开头，新增的中文数字长合同评测用例通过，verify.sh 全绿；clause-N 编号变化导致的基线更新要单独提交。
2. **【P1】交叉引用目标条款并入 must-read 候选**（`dsh_findings.candidates`）。用确定性规则缓解课程评论区指出的"条款跨分片互相引用、组合风险难发现"，不增加模型调用；未读时作为平台缺口如实报告。
3. **【P1】findings 记录补充证据契约字段**：`document_sha256`、切块器参数和版本、引文字符偏移、heading（16-13 讲）。这样审计时能从发布结果追溯到原文位置，切块改动后的影响也能定位。
4. **【P1】用真实 usage 标定字符估算**：每次调用记录 estimate_after 与 prompt_tokens 的比值，评测后输出分布（13-12 两讲）。成本很低，可以回答"70% 预算到底对应多少真实 token"，只观测不自动调节。
5. **【P2】已被取代的 submit_findings 参数掩码 + 跨 Run 失败码聚合**：前者补上 13-12b 评论区提到的 arguments 盲点；后者按 18-15 讲统计重复失败率，并把高频失败下沉为校验规则或评测用例。两项都是确定性改动，可测试。

## 四、诱人但不该做的 3 项

1. **LLM 摘要式压缩（Episodic Summarization / 模型可读摘要）**（12-11、13-12b、14-13a）。它会多消耗一次模型调用（8 次上限），而摘要可能把"不得""30 日"这类关键约束和数值弱化（14-13a 讲自己也承认"细节不可能 100% 不丢"）。被摘要的内容也无法再做逐字引文校验。现有的"存根 + 可回读 + 超限 fail-closed"已经足够，而且可以证明正确。
2. **为单份合同引入向量 RAG / embedding / reranker**（16-13）。项目只在一份文档内检索，平台已经有逐字子串检索和全量证据块，召回不足时由候选词表和缺口机制兜底。课程也强调"先治理知识源和切块，别急着调 top-K"，当前真正的问题在切块边界（见第 1 项）。引入向量检索会增加不可复现性和依赖，却解决不了逐字引文校验这个核心需求。
3. **按剩余窗口分档的动态编排（Full/Balanced/Compact/Minimal、L0–L4 多精度版本）和跨 Run 自动记忆或失败经验注入**（13-12a、15-12、18-15）。前者作者自己说"在实践中……性价比就不那么高了"，而本项目是 64K 窗口、8 次调用的单文档任务。后者会打开记忆投毒面，还可能把合同正文写进长期存储，违反"事件只记元数据、不记合同正文"的项目规则。失败经验应该下沉为平台校验和评测用例，不应该作为 prompt 记忆注入。
