## 工具契约不止是函数签名

T02 p2–7 把工具生命周期拆成六项：单一职责、模型可理解的描述、平台可判定的元数据、执行防重、可操作的错误和有界结果。它解决的是“模型挑了动作，谁负责判断这个动作能不能执行”，不是把权限提示写得更长。

在 DSH 中，模型只看到 search_document、read_clause，付款模板再增加 submit_findings。`dsh_runtime.py` 冻结每 Run 的 allowed 集合，`dsh_provider.py` 校验请求工具集合，`dsh_crossings.py:90` 校验平台票据与参数摘要。这已经对应了原子工具、平台准入和同进程回放，不能再把它列成缺失功能。

仍需完善的是错误可诊断性：SDK 本地拒绝了参数时，工具票据可能没有投递；下一模型轮现在得到 PREDECESSOR_PENDING，容易让人误以为工具还在执行。安全方向是拒绝继续，但错误应区分“未投递”与“执行结果未知”，不得为改善提示而跳过前置工具检查。

课程的执行示例不能原样采用。T02 p4 注释声称原子防重，但代码实际是 exists → 外部发送 → setex；两个并发请求可以同时通过检查，发送成功后进程崩溃也可能没有记录。当前平台明确保留 unknown、不承诺外部 exactly-once，比照搬这一段更符合实际边界。课程的“所有状态外置”也不能推出“绝对不能使用 Run 内缓存”：当前缓存只在同一活动 Run 内回放，丢失后拒绝重新执行，不承担跨进程恢复。

## 成本必须在实际发送前约束

O15 p1–4 的主线是按任务、步骤及子任务记账，用轮数、时间、Token 与金额控制失控；p5–6 讨论模型路由、降级与稳定前缀，p7 提醒“工具动作变了”不代表取得新信息。

当前 `business_budget.py` 在事务中预留，再标 sent，返回可靠 usage 才结算；未知用量保持冻结。`dsh_runtime.py` 的每次主调用都经过这条边界，纠正提交也不另开账。8 次模型上限、32 次工具上限、Run 截止时间和按证据判定的无进展停止是不同的约束，不能互相替代。

需要避免三个误用。第一，课程 p2–3 的“每轮前后查账”不足以证明并发硬上限：两个动作可同时看到同一剩余额度，必须先原子预留。第二，课程中的美元示例不能代替本项目套餐计费；`max_cost_minor=0` 表示不批准额外余额付费，不是零成本或 Token 耗尽。第三，不采用隐式切模型、自动追加预算或降低发布要求；这些会改变已冻结的 Task 与授权。当前保守容量预留可能提前拒绝一个本可完成的小任务，这是吞吐取舍，不宜通过未校准字符估算放松。

下一步应把模型轮次、预算调用 ID、耗时及退出原因明确关联，让一次失败能回答“没发送、已发送但未知，还是已结算”。不能用 crossing 的 failed 总数当 Provider 错误率：当前未使用的下一轮票据也会被退役为 failed。

## 可观测性需要真实状态而不是更多正文

O16 p1–3 强调：HTTP 200 和工具成功只说明动作执行了，无法证明授权与业务意图正确。Trace、Span、Generation、Session、Score 用来关联任务、调用与质量。p4–6 提出轨迹漂移检测、不可变记录和分层存储。H29 p1–3 则给出更适合单体起步的路线：先统一结构化字段、调用关联、耗时和错误分类，再决定是否需要整套外部观测系统；p8–10 强调告警应符合实际业务影响。

平台已有 Run、递增事件、模型用量、上下文摘要、工具证据 ID、提交历史和 crossing 状态。它不是黑盒，也未实现完整请求重建。`dsh_crossings.py:32` 的 retire 把 issued 记为 failed，`dsh_runtime.py` 又在 run.succeeded 之后的 finally 调用 retire；因此成功轨迹尾部会多出一条看似失败的调用。这是观测语义的具体缺口，不是缺少一个 Grafana 页面。

拟议第一项优化是明确未执行票据的 retired 状态，并把正常成功/失败收尾中的退役与终态放入同一事务。取消竞争要单独验证：已经返回的取消终态不能为了美观而阻塞等待远端，迟到的 unknown 结算仍可能发生，不能承诺“任何终态之后绝无审计”。历史 failed 记录不凭猜测重写；新事件应有清晰版本，聚合只把真正进入执行的调用作为分母。

O16 的完整输入输出和推理记录建议不适用于当前 metadata-only 契约。这里只采用关联 ID、摘要、固定类别、用量与耗时，不在观察事件里保存合同、模型正文或原始异常，也不自动接入外发遥测。

课程中另有两个可独立验证的逻辑问题。O16 p4 说“替换工具但集合相同”，仅在列表里还存在相应名称等附加条件下成立；单纯把 A 替换为未出现过的 B，集合差也能发现。它的 zip 逐位比较还不能直接实现“允许插入其他合法动作”的子序列契约。H29 p8 把状态 0/1/2 的 min==1 当“全部 OPEN”，但 [1,2] 也满足；应验证所有预期 Provider 均存在且均为 OPEN，不能仅照抄表达式。

## 测试同时验证边界和可完成性

Q18 p1–2 区分框架控制逻辑与模型能力；p3–4 提出把真实故障固化为回放材料并绑定数据集版本；p5–6 要求对调用轨迹断言，而不只匹配最终答案里的关键词。这三点值得采用，但不等于真实模型测试可以取消。

已有官方 DSH SDK 加合成 Provider、独立 review 探针、定向突变和真实豆包小样本验证，分别证明控制逻辑、反例强度和协议兼容性。下一批应补一个统一的轨迹检查口径：未准入动作不能执行；回放不能重复记账；失败/取消不能发布；unknown 不能当零花费；合法样本仍然能完成。这样既能发现越界，也能发现“全部拒绝所以全绿”。

不采用把生产合同的完整请求响应直接录入公开测试集。事故应先转成获准的合成夹具，并保留其行为因果、版本和请求匹配；当前只有摘要的事件不足以自动还原原始模型现场。Q18 p4 的 Replay 客户端只按 cursor 返回下一响应，不能自行证明请求匹配，也不能证明末尾没有未消费响应；这两项应成为回放器的独立反例。

课程 p6 的 evaluator flake 不阻断，必须区分指标类型：可选质量评分不可用可以标为未评估，但授权、泄漏、预算这些硬门禁没跑出结果时不能当 PASS。当前没有引入课程的在线评分或告警平台，本批先完善确定性的生命周期和轨迹证据。
