# 第十九批 工具护栏与发布控制

护栏是否有效，取决于它真正控制哪一次执行或发布，而不是规则有几层。前置拒绝可以阻止动作，后置拒绝只能拦住后续使用；已经外发的数据和已经产生的费用不能靠屏蔽结果撤销。DSH当前最重要的边界仍是平台持有模型发送权、工具许可和最终发布权。

## 合同护栏管道的价值与漏洞

G18 p1–4提出把危险命令、外发域名、敏感信息、文件访问和成本规则挂到工具调用前；规则按顺序pass、block或rewrite。p5–8给出具体检查，p9强调把控制放在模型之外。方向正确，但示例的保护范围比“所有危险操作”窄得多。

1. **正则前筛限制了语义检测的覆盖面。** p5声称LLM补充发现非格式商业秘密，p6代码却在正则零命中时直接放行。这种两段式流程可以复核格式误报，不能发现所有正则未命中的语义秘密。LLM出错又返回空列表，最终会把本来可疑的输入放行，属于fail-open。
2. **检测调用本身就是外发。** 把完整工具参数发给另一个模型前，也必须通过数据使用授权、预算与取消检查。不能先泄露给检测模型，再用它的答案证明没有泄露。原示例用当前模型，并未展示独立的可信本地分类器；“便宜小模型”只是正文建议。
3. **域名后缀缺少标签边界。** p7的`hostname.endsWith(domain)`会让`notgov.cn`匹配`gov.cn`。应至少区别域名相等与点分子域，另处理协议、端口、解析及重定向边界。允许某个网站也不代表可以把合同放进它的query参数。
4. **字符串路径前缀不是目录权限。** p7的`absolute.startsWith(cwd)`会接受同前缀的兄弟目录，`path.resolve`也不会解析符号链接；仅拦read还挡不住bash或自定义工具的文件访问。黑名单片段既可能误拒正常名称，也无法穷尽敏感路径。
5. **工具调用前检查累计Token，不是模型发送预算闸。** 即使工具被拒，循环仍可能再问模型；重试、压缩和检测辅助调用也不在这一事件内。G18 p8把成本规则放在管道最后，还可能先花掉检测模型的费用。实际预算必须覆盖每次发送与未知用量，而不只是返回一句“超预算”。
6. **审计先投影再持久化。** 示例在运行规则前调用`logToolCall`，结果又直接记录；其日志函数未展示，不能认定已脱敏。本项目不能把这段位置关系照搬为原始参数落库，也不能让检测结果的reason包含敏感内容摘要后再回传或外发。

其中域名与路径两个条件已用本地Node无网络表达式复现：后缀条件和兄弟目录前缀条件均返回true。这里只验证示例表达式，不声称运行了作者的完整项目。

### Pi固定版本下的顺序与改写

Pi f07218c4的`packages/agent/src/agent-loop.ts:719–723`先准备并验证参数，再调用beforeToolCall，和课程p1图中的“tool_call之后才参数校验”不一致。`coding-agent/src/core/agent-session.ts:537–542`把已验证args放入新事件对象的input字段；`extensions/runner.ts:1134`分发事件并返回拦截结果。

因此G18 p4的`event.input = result.input`替换的是事件字段，不会把原先的validatedArgs变量指向新对象；底层仍在`agent-loop.ts:762`返回原args。修改共享对象的内部属性是另一回事，但也不能据此跳过修改后的参数校验。一个最小JavaScript对象引用探针同样显示，替换事件属性不改变原参数对象。这里是固定版本源码结论，不是已运行完整Pi端到端探针。

该版本的工具钩子抛错可阻止本次工具执行，不等于终止所有后续模型请求；before_provider_request又有不同的异常语义。不能把“某个handler抛错”当作所有层通用的硬拒绝机制，详见已复审的Pi源码讲解及本批Hook对照。

## 前置执行后置与补偿

G25 p1–7清楚区分三件事：输入拒绝时动作未执行；输出拒绝时原始结果已存在；异常时外部效果可能仍已发生。p6列出UNKNOWN并要求先查明结果，p10–11说明标记需要回滚不等于真正补偿。这些表述比单纯try/catch后二选一成功失败更适合真实系统。

p7–9还补充了审批后重查对象状态、影子规则与强制规则、原Handler旁路和最小凭据；p10的跨工具数据传播与契约版本漂移提醒我们，单次参数合法不足以证明整条行动链合法。p13的五类压力矩阵适合设计回归，但最后一格“无”只表示该组教学故障没有暴露，不是系统不存在其他风险。

采用时仍需补齐：

- 课程明确承认金额缺字段会被阈值钩子放行，需要前置Schema；Tool Registry公开也存在绕行。不能把正文提出的生产要求当作教学实现已完成。
- 原请求、有效参数、原输出、发布输出的语义要分开，但不必全部以明文落库。平台应使用受控产物或摘要引用；原始异常拼接同样要去除敏感信息。
- 影子模式不能替换既有强制防线。只记录BLOCK并不保证没有副作用：如果规则本身改了effective_args、发了请求或消耗Token，也必须隔离和计费；不能仅通过`blocks=False`推断完全无影响。
- 守卫崩溃时拒绝只是当前执行入口的行为，还要检查所有旁路。后置检查也不能保护已经在检查之前流式发给用户或写入日志的原文。
- 补偿是新的受权动作，需要自己的幂等、预算、状态和外部确认；不能因为标记rollback就自动扩大权限、执行退款或重试原动作。

## 与当前DSH的对应

| 边界 | 当前机制 | 仍需保留的限制 |
|---|---|---|
| 工具准入 | Run冻结允许集合，平台严格校验参数与条款ID | 不开放任意bash、网络抓取或业务写入；不是OS沙箱 |
| 模型发送 | 平台账本预留后发送，未知用量冻结，不自动重试 | SDK钩子和工具成本提示不能替代此入口 |
| 结构化校验 | 最后一次提交须有效，引用须来自本轮实际读取 | 数值/单位/主体校验不证明语义蕴含 |
| 发布 | 付款模板由平台根据校验结果生成正文，再事务内核对状态 | 不是把模型最终文本事后贴上“已校验”标签 |
| 失败审计 | 固定错误类别、正文摘要、提交序号与计划证据 | 不为复盘把合同或stderr原文重新写入事件 |
| 调用效果 | HA83身份与回放，HA85未使用退役和unknown区分 | 本地收据不证明外部exactly-once，未知结果不重发 |

因此本轮不增加LLM敏感信息二次确认、不新增通用“护栏框架”。更有价值的是确认既有每条路径都经过平台入口，并用旁路、取消、重投、错误分类和发布反例锁住边界。研究结论不能自动授予真实敏感合同或新网络工具权限。
