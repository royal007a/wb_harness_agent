# 第三批：安全边界与测试可信度

最重要的取舍：**不采用“数据打高分就能成为指令”，也不采用“测试大部分通过就算安全”。** 对当前 DSH，最小工具集合、平台控制发送与发布、账本和取消、正文不进观察事件，比再加一个未校准的风险分更有用。课程的治理方法可以借鉴，示例代码和强保证需要逐项检查。

本批全文阅读六篇42页，累计16篇140页。包括评论；另渲染核对人工审批讲 p2 的代码。不是183份全部读完。完整来源哈希在[清单](JIKESUMMARY_SOURCE_INVENTORY_2026_10_06.json)，只上传原创归纳。代码基线为研究分支 `b080743`；HA-0085/0086 尚在复审与全量验证，没有据此部署。

## S11：角色授权之外，还要限制任务、数量和出口

p1 的三个风险是合法只读接口被反复枚举、读数据再外发的组合风险、任务结束后凭证残留。p2–4 用任务级委托、短期令牌和参数规约收窄权限；p5 区分工具出口与模型请求出口，p6 讨论安全熔断，p7 评论强调续期时重新校验。

可吸收的是这四个约束，而不是强制引入 MCP/OAuth 全套基础设施。DSH 的临时网关能力令牌按一次 adapter 生命周期生成，模型服务凭据只在平台发送路径解析；工具只操作本 Run 的 clauses，参数严格检查、总工具次数受限。`adapters/dsh.py` 的临时网关与 `backend/dsh_runtime.py` 的工具执行/计数、`backend/dsh_provider.py` 的固定模型出口是三个不同层次，不能合称“已实现企业 OBO”。

需要修正的课程推断：

- 单次 limit≤50 不会切断多次枚举；还需要资源范围授权、累计配额和行为约束。
- TTL 到期失效不等于任务结束立即吊销。立即结束的委托需要网关状态或其他撤销机制，不能只等时间。
- 工具网关看不到所有模型请求，也不自动封住操作系统网络出口。本分支没有 OS 级网络沙箱，仍只允许公开/合成文本；关闭 shell 等模型工具不等于防住被攻破的宿主依赖。

目前不开放邮件、外部搜索、任意 HTTP 或真实敏感文档。未来若扩展出口，应先做数据流与累计授权设计，而不是把现有只读工具白名单外推成通用 DLP。

## S12：让人批准明确的动作，不让人替系统猜风险

p1–2 的主线是审批疲劳、证据不足和等待状态不持久。p2–3 把执行、拦截、策略、审批单管理和人类判断分开；p4 提供操作目标、影响和依据，超时默认阻断；p5 讨论异步解耦和追踪。

值得吸收的是持久化审批状态、准确证据包和拒绝默认执行。p2 的反例除了阻塞线程还有更直接的漏洞：`approval=False` 时仍会落到最后的 execute_tool。已按 PDF 渲染核对，不是抽取缩进丢失。课程将它列为错误做法，但产品验收必须明确断言“拒绝/超时不执行”，不能只把同步改异步后保留同样的分支。

“高危动作等待批准”与“占着线程永久等待”不同。异步本身不提供持久化，也不保证审批绑定正确。审批必须绑定主体、动作、参数摘要、目标资源版本和期限；参数或权限变化要重查。紧急升级是新的授权，不是超时后自动绕过。模型生成的摘要不能替代真实目标和影响范围。

当前 DSH 没有需要人批准后执行的外部高危工具，不借此添加审批中台或 Kafka。仓库中的业务 Gate 与工具执行批准是不同契约，也不能因为有 Gate 就声称上述工具审批已经接入。未来确有高风险能力时再按作用域设计最小持久审批，不复制课程的全套拓扑。

## S13：把信任边界落在执行处，而不是分数里

p1 说明自然语言约束不是强制隔离；p2–3 提出内容、来源、行为三个维度，p4 在输入、检索、组装、工具调用和输出五处评估；p4–6 根据风险采取不同处置并持续校准。

采用“工具返回也不可信、跨边界重新检查、行为序列也要看”。不采用下列安全保证：

- p3 将内部系统的高来源分作为进入指令区的理由，忽略内部系统可能存有用户提交或外部检索正文。存储位置不改变内容的授权属性。
- p4–5 给文本套 data 标签后提高信任分，只是提示组织，不是执行隔离；不能将正文升级成平台指令。
- p3 的祈使句密度和关键词检测无法覆盖所有注入，阈值也未在本项目标定。未命中规则不代表无攻击；合法安全审计材料也可能大量命中。
- 写入时审查不能替代查询时的主体权限、数据版本和组合上下文校验。完整审计正文也不符合本分支 metadata-only 的观察事件契约。

当前 DSH 在上下文尾部声明文档是数据，但真正的强制边界是工具集合、参数、票据、预算和发布校验。`payment_terms` 发布平台根据通过校验的结构化结果渲染的正文；free 模式保留较弱的草稿边界。两者都不保证语义正确。不能把有这些边界写成“Prompt 注入已解决”。

建议下一批安全测试使用合成注入材料，分别检查执行没有越权、事件没有正文、结果没有冒充平台批准；语义被误导则单独记录质量失败，不因为工具都合法就把它算安全正确。无权工具必须由平台拒绝，不能把“模型恰好没调用”当成护栏验收。

## J11：借鉴分层，不照搬框架名和空校验器

p1–3 是输入/输出护栏，p4–5 是 HTTP 身份和 Action 权限，p6–7 是目标选择与循环上限。这个分层有启发：身份认证、动作授权、预算与内容质量是不同问题。

但示例 ThinkingBlocksGuardRail 只是记录 thinking blocks 并返回通过，不能作为真实内容检查；照搬日志还会扩大正文泄漏。禁用一个 DeleteAccount 名字不等于禁止所有高危动作。轮数上限不等于输入大小或 Token 总上限，更不能自动覆盖辅助模型调用。未检查固定版本源码前，本文不保证框架的注解、异常或钩子分发语义。

当前平台已具备模型/工具总数限制、业务 Token 预留、Run 截止和取消；这些分别保留。无需引入 Java/Embabel 才能实现上述控制。HTTP 同源和可信本机边界也不能冒充生产认证或多租户隔离。

## Q14：先沿关键链路摸测试，再谈覆盖率

p1–4 的四步是找核心路径、查现有断言、实际运行、分类缺口。测试文件存在不代表路径被测，失败不能一概归环境；p4–7 把缺口收敛到可执行批次，评论也说明数量上限是教学安排，不应强制删真实风险。

对本项目采用“请求→平台执行→持久状态→产物→详情”的链路矩阵，不单数文件。课程按90%通过率给绿色的示例不适合作为发布门禁：一个权限/泄漏/预算测试失败仍然阻断。skip 和未测要单列；测试数量不是覆盖率。

一个实际新发现说明为什么不能把列表/分页普遍当非核心：本轮用临时库和合成桥发出600条观察事件，付款 Run 正常成功（3次合成模型调用，latest_sequence=633），终态计划 S1/S3/S4 都是 done，但详情中的三步仍是 pending。`dsh_runtime.detail()` 用只返回前500条的 `Store.events()` 重建计划，漏掉后面的变更。GET 本身零写入，问题是读到了旧投影；并非执行计划失败。这是离线平台探针，不是 SDK/真实 Provider/线上复现。后续独立切片修复并加分页边界反例，当前未修。

## Q15：现状回归不是把旧错误变成规格

p1–4 建议优先锁住改造路径的真实现状、用完整 HTTP→Service→DB 集成测试、对复杂纯逻辑补边界，分批审查；p4–7 要求 CI 真正运行；p8–9 的评论涉及 mock 和录制回放。

采用前后对照、小批独立复审和真实临时数据库。但 Characterization Test 只记录现实，不批准既有缺陷。规格明确修复的行为，旧版本应该在真实断言处失败；不能为追求兼容保留漏洞，也不能把导入失败当行为反例。

课程提到的小日志改动，在本项目可能正是正文泄漏路径，不能一概免测。mock 验证本方控制和错误分支，不证明 Provider 协议、SDK 初始化或真实 socket 兼容；mock 掉被改的 DAO，也不能证明实际 SQL 和事务回滚。实际调用边界必须单独验证。

仓库当前没有 `.github/` 工作流目录，有本地 `harness/verify.sh`。这不等于 GitHub 已强制检查：工作流存在、一次跑绿和远端 required checks 是不同事实，本文未核对仓库保护设置，也不声称已经配置。当前先把本地失败定位清楚，不用新增 CI 配置掩盖不稳定测试。
