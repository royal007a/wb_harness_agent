## 2. 第 07 讲：记忆要会“遗忘”

### 课程讲了什么

- 事故：用户三个月前把套餐从 VIP 降为基础版，图谱里的事实已更新到 v2，但向量库里一条旧偏好（喜欢 VIP 权益）和新情节语义相近，被一起召回，模型在新旧并存的上下文里“猜”成 VIP。根因不是召回不到，而是**记忆只进不出**。
- 遗忘不是 TTL 硬删：会误杀常用记忆，又放过刚写入却已冲突的记忆。课程给两个互补机制：
  1. **召回时实时算激活值**（ACT-R）：`激活 = 时间衰减 e^(-t/S) + 频率增益 0.2·log(1+n) + 近期增益（7 天内 +0.3）`，纯函数不缓存；约束和事实恒为 1.0，偏好无 TTL 恒为 1.0，只有情节记忆衰减；低于阈值（示例 0.05）当场跳过，命中后异步回写访问次数。
  2. **写入时增量整合**：冲突只发生在相似记忆之间，所以拿新记忆当查询取 Top-K（示例 K=10）相似旧记忆交 LLM 裁决：新胜则旧的标 `superseded=True`，旧胜则新的不落盘（去重）。不做全库两两比对（1000 条约 50 万对）。
- 思考题：LLM 冲突判断会误判，被冤枉的记忆静默戴上 superseded 帽子、永远不再出现。提示方向是“软删除窗口 + 召回命中自动复活”。

### 对照当前实现（代码事实）

- DSH 路径**没有跨会话记忆**：每个 Run 独立，DSH 会话目录随 Run 结束清理（`adapters/dsh_workspace.py`）。
- 平台另有 Memory Plane（`backend/memory.py`）：显式 Source/Fact、`supersede` 时旧事实标 `superseded` 并记录 `superseded_by_fact_id`（约 400–419 行）、有效期与 `as_of` 可见性；语义检索门禁关闭。DSH 未接入它。
- Run 内的“新旧并存”问题我们已经遇到过并处理：结构化提交以**最后一次为准**，被拒的替换会撤销旧的通过（HA-0079 返工）；被省略的证据只有在没有完整副本时才算“看不见”（HA-0081 返工）。

### 建议

- **暂不引入**激活值衰减和向量记忆：DSH 没有跨会话记忆需求，引入只会制造第 07 讲那类事故的土壤。
- 若将来要跨 Run 复用（例如“同一合同模板已知的例外条款”），走 Memory Plane 的显式事实 + supersede，不走向量偏好；并按思考题补两点：supersede 必须留可回溯的原因与操作者，误判可人工复原；复原与被替代都写审计事件。
- 一个现在就能吸收的小点见第 C 项：Run 内被替换的结构化提交目前只留计数，不留可回溯的版本，等于“静默 superseded”。

## 3. 第 08 讲：计划必须是系统数据，不是模型的心里话

### 课程讲了什么

- 事故：数据库灾备迁移的第 3 步（传输）被防火墙挡住，ReAct Agent 因为“第 2 步”只存在于临时思维里，判断“全部重来”，重复执行 30 分钟的全量 Dump，触发 IO 与主从延迟告警。
- 公式：智能体系统 = 概率模型 + 确定性循环 + **持久化状态 + 故障恢复**；ReAct 只有前两项。
- 三道防线：
  1. **计划数据化**：`PlanStep{step_id, action, params, depends_on, status, output_ref, error, version_created, replaces_step_id}`；`Plan.get_parallel_ready()` 按依赖找可执行步骤。模型只“建议修改”，系统“执行与改写”。
  2. **增量重规划**：失败步骤保持 FAILED，`mark_downstream_obsolete` 只把未完成的下游标 OBSOLETE，**已完成步骤保留并复用产物**；`merge` 校验依赖存在、不依赖作废步骤、无环；`replaces_step_id` 指向的旧步骤无论状态都强制作废（防模型“替换已完成步骤”造成两份并存）。
  3. **事件溯源 + 检查点**：PlanCreated/StepStarted/StepCompleted/StepFailed/PlanReplanned 追加写，`replay_to_version` 可回放；检查点用于快速恢复，崩溃后跳过已完成步骤。
- 附录：金融合规审计的 Plan 里，不可逆的 `submit_to_regulator` 标 HIGH 需人工审批；审批拒绝后用 `draft_sar_for_review` 替换，已完成的分析步骤不重跑。评论区作者强调“全链走完才交控制权”这类约定要钉在 `depends_on` 或脚本里，不能靠主 Agent 自觉。

### 对照当前实现（代码事实）

- DSH 付款核对是典型的**隐式计划**：平台在提示里说“检索并读取期限、触发、例外、冲突，然后提交”（`backend/dsh_runtime.py` 组装 prompt 处），之后每一步做什么完全由模型决定。
- 平台已有的“半个计划”：四个槽位与平台缺口（`backend/dsh_findings.py`）、例外候选清单（字面词表）、按轮进展判定与提前停止、上下文组装器里的可信状态（已读块、未读例外候选、提交次数）。这些都是**事后校验**，执行前用户看不到要核对什么，执行中也看不到走到哪一步。
- 失败恢复：进程重启时 Run 直接以 `DSH_SERVER_RESTARTED` 失败（`recover()`），不续跑；重新执行是新 Run，**之前读到的证据全部重来**。这是 HA-0077 有意的安全选择（不重放状态未知的模型请求）。
- 平台控制面另有 `plan-revision@1` / `gap@1` 与 Replan TCC（CSV 固定统计路径），但 TD-022/023 明确不得称为通用计划编辑，DSH 未接入。

### 建议（A 项，见第 6 节）

把付款核对的固定步骤变成平台拥有的计划数据：执行前可见、执行中逐步更新、失败时指出卡在哪一步、重跑时复用已完成步骤的**平台证据**（不复用模型会话）。模型仍决定怎么搜、怎么读，但“这一步完成了没有”由平台根据证据判定。

## 4. 第 09 讲：Agent 之间的每次交接都要过“海关”

### 课程讲了什么

- 三类故障：上游把一周的历史和情绪全塞给下游导致越权；下游交回 8000 token 的试错史污染上游和 Prompt Cache；“绝不能删除数据”只写在上游系统提示里，交接时蒸发。
- 所有协作形态（委派、接力、共享会话、黑板、任务池）拆到最小都是一次“过境”：下发、回传、转交、发言、写入、领活。与其每种形态各写一套，不如统一一个**治理平面**。
- 下行：任务包由框架代码组装，模型只能填 `task` 一栏，约束显式作为字段携带，大数据只传引用——“最好的过滤是不需要过滤”。
- 上行：五道关卡顺序固定——身份核验（`message_id` 防重放）→ 结构裁剪（剥 reasoning/thoughts，截正文）→ 契约校验（必填字段与类型，未申报字段剥离）→ 安全门（内容/注入，由应用注入检查器）→ 审计（只记录真正过境的东西，放最后）。拒收进 review queue，上游只收到“被拒”短消息。
- `Crossing{message_id, trace_id, direction, kind, from_agent, to, payload}`。契约关只验形状不看内容，好坏由业务检查器负责。
- 作者回复：A2A 管“邮政”（能力名片、任务状态、身份），治理平面管“海关”（准不准入），二者互补。

### 对照当前实现（代码事实）

DSH 目前是单 Agent，但“平台 ↔ DSH 子进程 ↔ 模型”之间已经是一条过境链，多数关卡已有对应：

| 课程关卡 | 现有实现 | 缺口 |
|---|---|---|
| 下行任务包由代码组装、约束显式携带 | 提示与工具集合由平台按模板生成；上下文组装器追加平台可信状态并声明文档是数据（`backend/dsh_context.py`）；system persona 在 `dsh-adapter/controlled.patch.yml` | — |
| 身份核验 | 网关 Bearer capability，未授权只回 403（`adapters/dsh.py`） | **无 message_id 去重**：`/tool` 请求体只有 `{name, arguments}`（`platform-plugin.mjs:81`），同一次工具调用若被重投会执行两次（当前工具只读，`submit_findings` 会多计一次提交） |
| 结构裁剪 | Provider 响应只取 content 与 tool_calls，`reasoning_content` 等丢弃（`backend/dsh_provider.py` `parse_response`） | — |
| 契约校验 | `submit_findings` 严格 schema + 机械校验；付款模板只发布平台根据校验结果渲染的正文 | 自由模板最终文本只查引用，契约较弱（保留为草稿边界） |
| 安全门 | 文档不提权；工具参数白名单；敏感输入拒绝 | — |
| 审计 | `dsh.tool.completed`、`dsh.findings.checked`、`dsh.context.assembled` 只记元数据 | **没有统一的过境记录**：模型调用、工具调用、提交三类事件各记各的，无同一 `trace_id`/`crossing_id` 串起来；被拒的过境只在部分事件里有固定错误码 |

### 建议（B 项）

- 给网关的 `/tool` 与 `/model` 请求带上 DSH 的 tool_call_id / 调用序号，平台按 `(run_id, crossing_id)` 去重：重投返回首次结果，不再执行。
- 统一一条 `dsh.crossing` 元数据事件（方向、种类、调用序号、结果：delivered/rejected/replayed、固定错误码、摘要哈希），把现有三类事件串成一条可追溯链；不写正文。
- 不为多 Agent 预建治理框架：DSH `sdk-minimal` 未启用子代理，等真有第二个 Agent 再按本讲的口岸模型扩展。

## 5. 第 10 讲：并发时先隔离，再原子，最后才加锁

### 课程讲了什么

- 三类故障：读改写覆盖（进度文件丢更新）、孤儿锁（持锁进程被 OOM 杀掉）、死锁（交叉等待配置锁与数据库连接）。
- 主流框架（LangGraph、Claude Code）不内置声明式工具锁：框架不懂业务语义，分布式锁会让框架变重。
- 上策**隔离**：空间隔离（Claude Code 用 git worktree，隔开的不只是文件，也是“认知空间”，避免读到语义上的中间状态）；状态合并（LangGraph reducer）。
- 中策 **Tool 层自卫**：判断与写入合成一条原子 SQL（`UPDATE … WHERE status='pending'` 看 rowcount）；**重试范围里不能夹 LLM 调用**（`while True` 里读→LLM→CAS 会让 LLM 白跑），冲突即失败、交给调度层重派；锁要有 TTL，续约绑定主事件循环（主循环卡死则续约停止、锁过期），不要在 Tool 里裸开后台线程续约。
- 下策 **Agent 的修养**：工具返回 `RESOURCE_BUSY` 与 hint，Agent 改做别的。
- 决策表优先级：无锁 → 隔离 → 抢占 → 乐观锁 → 悲观锁。

### 对照当前实现（代码事实）

- **隔离**：每个 Run 独立 `HOME/cwd/TMPDIR`，平台 mkdtemp + 登记 + flock 租约 + 进程组（`adapters/dsh_workspace.py`）。租约用 `flock`，持有进程死亡时由内核释放，比 TTL 更直接，不存在孤儿锁。
- **原子抢占**：Run 从 queued 到 running 在事务内判断（`execute` 开头），已有“并发执行只认领一次”的测试；预算预留在 `BEGIN IMMEDIATE` 事务里检查余额（`backend/business_budget.py`）。
- **LLM 不在 CAS 重试圈里**：预算是“先预留、发送、再结算”，不是乐观锁重试；模型调用失败不自动重试。
- **实际并发度**：本地服务只有一个 worker 线程（`backend/service.py` 的 `local-worker`），8876 上的 DSH Run 是串行执行的；并发只在测试里用线程池模拟。
- 已登记的小缺口：重启恢复时若旧 bridge 尚未退出，工作目录被标 pending 后**没有延迟重试**，残留要等下次重启（HA-0077 复审 Low，tech-debt 已记）。

### 建议（D 项）

- 不引入锁管理器，不改单 worker 模型。
- 补 pending 工作目录的有界延迟清理重试（沿用租约/进程组/设备 inode 检查，不杀恢复出的 PID）。
- 如果将来把 worker 提到多线程，再补“同一文档资源多 Run 并发”的测试；当前资源表按内容哈希 `INSERT OR IGNORE`，只读共享无写冲突。

## 6. 优化计划

全部是建议；实施前各自建 Work Item（编号接 HA-0082，HA-0090 已预留给智能客服）。均不改上游 DSH Loop，不开新工具类别，不调用额外模型。

### A（P0）付款核对计划数据化——第 08 讲

**解决的问题**：执行前看不到要核对什么；执行中看不到走到哪；失败只给一个错误码；重跑从零开始。

**最小设计**：
1. Run 创建时，平台为 `payment_terms` 生成一份**平台计划**并作为产物/事件登记（`dsh-plan@1`）：
   - S1 定位付款条款：完成条件 = 平台计算的付款相关证据块全部已返回给模型（搜索分页走完或逐块读取）。
   - S2 读取例外候选：完成条件 = 平台例外候选全部已读（或明确列为缺口）。
   - S3 提交结构化结果：完成条件 = 最后一次提交通过校验。
   - S4 发布：平台渲染并发布。
   每步 `{step_id, title, depends_on, status, evidence_refs, error_code}`，status 由平台根据证据和校验结果更新，**模型不能改写计划**。
2. 执行前：页面在创建 Run 后立即显示这份计划和平台识别出的候选证据块编号（不含正文）。
3. 执行中：每次工具调用/提交后更新步骤状态并记 `dsh.plan.step` 元数据事件；可信状态消息里告诉模型“当前在哪一步、还差哪些块”。
4. 失败：Run 失败时记录卡在哪一步（例如 S3 连续三次未通过、S2 有两个候选未读）。
5. **断点续跑（基于平台证据，不基于模型会话）**：用户对失败 Run 发起重跑时，新 Run 继承上一 Run 已完成步骤的**平台证据记录**（已读块编号、已校验的槽位），新 Run 的模型从“已读块清单 + 剩余步骤”开始，不重放上一 Run 的模型请求，也不复用其预算。继承关系用 `based_on_run_id` 记录。

**不做**：模型生成 DAG、任意计划编辑、跨模板通用计划引擎（TD-022/023 的边界不变）。

**验收**：
- 计划在第一次模型请求前已持久化，页面可见；
- 步骤状态只能由平台规则推进，模型请求中伪造“S2 已完成”无效；
- 第二讲旧探针场景（只读前三个搜索结果）在计划里表现为 S1 未完成或 S2 有缺口；
- 失败 Run 的 `run.failed` 带 `failed_step`；
- 续跑 Run 不重读已读块也能通过（合成 Provider），且不继承旧 Run 的预算预留；真实豆包至少跑 3 份对比续跑前后模型调用数。

**代价**：新增一个产物 schema 与一组事件；续跑要处理“上一 Run 的证据是否仍对应同一文档哈希”（必须校验资源哈希一致）。

### B（P1）网关过境账本与重放防护——第 09 讲

- `/tool`、`/model` 请求携带 DSH 的调用 ID（工具为 tool_call_id，模型为调用序号）；平台在 `(run_id, crossing_id)` 上去重，重投返回首次结果且不再执行、不再计数。
- 新增 `dsh.crossing` 元数据事件串起模型调用、工具调用、结构化提交：方向、种类、结果（delivered/rejected/replayed）、固定错误码、摘要哈希。
- 验收：同一 tool_call_id 重投两次只执行一次、`submit_findings` 只计一次；事件里没有正文；被拒过境有固定错误码。

### C（P1）结构化结果版本可追溯——第 07 讲思考题在 Run 内的对应

- 现在被替换或被拒的提交只留计数。改为每次提交都写一个**版本化的受控产物**（`dsh-findings-attempt-N.json`，与最终产物同一数据边界），记录被拒原因代码与是否被后续提交取代；最终产物引用其来源版本号。
- 这让“为什么最后结果是这样”可以回溯，也为人工复核时“复原”某个被替换版本留出入口（复原必须由人触发并记审计事件，不自动复活）。
- 验收：三次提交（拒、过、被替换拒）全部可查；事件仍只记元数据；产物大小受现有 64 KiB 限制。

- 锁管理器、悲观锁（第 10 讲）：隔离与原子事务已覆盖现有并发面。
