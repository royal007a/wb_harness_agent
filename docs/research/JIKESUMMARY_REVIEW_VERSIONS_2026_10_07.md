# 第十一批 生成评审与发布版本绑定

生成者负责提出候选，评审者负责提供可核实的观察，平台规则负责决定是否发布。最值得吸收的不是再增加一次模型打分，而是保证最终发布的版本确实经过相应检查，并且检查覆盖了业务风险。

本批全文阅读一篇15页，核对第3页代码图，累计34篇374页。项目定位固定在4b8ec1e；未运行课程配套仓库，也未新增真实模型裁判。

## 来源和逐段总结

来源为`测试质量/30 - 27｜生成评审：让每个版本独立接受审查.pdf`，SHA-256为`96265dd9537509e2d3425bba0af6d5782804d223c01ef46f1ec5ac4fa0822c96`。

- p1–3分开生成、评审、确定性策略和修订四个角色。模型提出问题、分数和理由，不直接拥有发布权。
- p3–5对单条异议和低分都要求依据；无依据意见保留为被排除的记录，不直接触发自动修改。两个输入桶重新分类，防止上游把有效异议藏进忽略项；容器转成tuple，避免事后增删成员。
- p6–8区分本次真正评审的版本与刚生成的修订草稿。草稿必须再次提交；生产回执应绑定内容摘要、版本、评审器、规则和证据快照。课程明确说正式ReviewReceipt还是设计蓝图，不能当作示例仓库已经实现。
- p9–11区分护栏与产出评审：同一检查放在执行前是动作准入，放在产出后是版本验收。第一遍修订的稿件仍是UNREVIEWED，第二遍独立检查后才能通过。
- p12–15通过移除账本证据的对照实验说明“调用过评审器”不等于有效审查。数量、总额都一致仍可能存在互相抵消的逐项错误，课程也明确要求按业务主键核对。评论补充证据时效和摘要绑定。

## 示例不能当成完整生产校验

第3页正文说检查名和证据必须同时存在，展示的`grounded`却只检查`evidence.strip()`，没有检查`check`。这是该页文字与代码的差异；本文没有核验配套仓库是否另有修正。非空字符串本身也不证明来源存在、证据真实、仍然新鲜，或与被审问题相关。

第4页用tuple冻结的是成员集合，不由此推出每个嵌套Issue都不可变。若生产实现把可变对象放进去，仍须对嵌套内容和裁决后修改单独测试。这里不在未读完整Issue定义的情况下断言课程仓库存在该漏洞。

策略没有找到可执行的反对理由时返回ACCEPTED，只能说明当前规则未阻断，不是证明业务正确。课程的“橡皮图章”实验正好展示这一点。对付款核对尤其要防止“所有引用合法，因此结论必然被支持”的推论。

## 当前实现对应关系

| 课程要求 | 当前合同Runtime | 限制与后续验收 |
|---|---|---|
| 修订不能继承旧批准 | `dsh_runtime.py:384`起每次submit先清空accepted；拒绝或覆盖缺口会撤销之前的通过 | 拒绝后结束必须不发布，不能只测试“首次拒绝” |
| 发布被审版本 | `dsh_runtime.py:450`起payment_terms要求最后提交通过；发布正文由render_findings生成 | free模板仍是独立的草稿边界，不套用付款模板结论 |
| 留下版本关系 | `dsh_runtime.py:394`起历史记录序号、摘要、错误码和superseded_by | 被拒正文不落事件；元数据历史不等于能还原全部候选正文 |
| 发布检查和终态一致 | 产物、最后计划和run.succeeded在同一Store事务中写入 | 并发取消、审计写失败、产物写失败要用故障注入验证 |
| 业务事实独立核验 | 原文引文、数值、单位、主体和已读条款由平台校验 | 不验证语义蕴含；数值都对也可能把“允许”写成“禁止” |
| 限制无尽改稿 | 纠正调用走相同预算账本和模型调用上限；有拒绝次数及无进展停止 | 增加submission_number本身不算获得新证据 |

HA-0088另把固定合成评测的期限评分与生产校验器分开，按完整数字和单位核对，避免“30包含在300中”导致错误绿灯。该评分器只认识固定脚本语法，不是通用语义裁判，生成理想fixtures通过也不能替代真实DSH链路评测。

## 下一步取舍

优先保留现有机械检查、固定版本复审和分层发布证据。若以后增加模型评审，应先登记它能看到的证据、覆盖的风险、最大调用与费用、独立人工金标，以及错误放行和误拦指标。不要用一个总分覆盖确定性反例，也不要让生成者修改验收标准。

代码复审、离线回归、真实模型兼容和部署健康应绑定各自的固定版本。文档或测试提交不改变运行代码时可以说明差异范围；运行代码变更后不能借用旧版本批准。当前HA85–89仍等待独立复审，全量浏览器导航超时尚未查明，不据定向通过签发部署完成结论。

本批不引入额外模型、自动改稿服务、外部遥测或新发布权限。
