# 第二批：Plan、Replan 与长合同上下文

结论先行：当前 DSH 最值得吸收的是**用平台事实判断进展、区分失败现场与根因、验证恢复依据**，不是再增加一个模型生成的通用 DAG。已有四步计划、提交校验、调用账本和上下文省略机制，应先保证它们的状态真实、错误可诊断、历史完整。证据续跑仍是单独设计，不能把旧 Run 的“读过”直接当成本轮模型已经看过。

## W05：计划要把五类不确定性显式化

p1–3 区分目标、上下文、路径、执行过程和失败处理的不确定性。p4–10 的五个关注点是 Goal、Context、Choice、Checkpoint、Correction：先定义可检查的目标；把已知事实、缺口和约束分开；比较候选路径；在关键依赖和业务里程碑检查；失败后有受控修正。p11–13 讨论评测、迭代和依赖图，特别要求循环依赖最终由代码检查。

值得吸收的是“计划有可核查的成功标准”，而不是它的缩写。G4C 是作者自己的助记方法（p13 明说），不是行业标准；同页关于借大公司或访谈名义背书的建议不采用。引用必须如实归属。p6 对 System Prompt 的强作用描述也不能当权限保证：模型生成的计划、检查点和“完成”声明都只是输入，不是平台批准。

**现状映射。** `backend/dsh_plan.py:29` 的 `project()` 从实际返回的证据、最近提交状态和发布事实重新计算四步状态。它不生成任务 DAG，也不调度模型。后一次提交被拒会使 S3 回到 blocked；partial 是允许的业务结果；S1/S2 完成只表示词表候选已提供给模型。这个设计已经吸收了可见计划和检查点的一部分，不能再算作“缺少 Plan”。

**下一步边界。** 先检查列表、详情和历史事件中显示的计划是否一致；模型自评不能替代平台投影。若将来引入 Plan Verifier，其额外调用必须计入同一账本并设上限。暂不引入通用模型 DAG、模型自改目标或自主扩工具。步骤完成率、Run 成功率与用户目标达成率分开报告。

## W06：Replan 是受控修正，不是遇错就换条路

p1–4 讨论执行中如何选择最小修改范围：触发信号不等于必须 Replan，可以停止、澄清或局部修正。p4–7 建议先由代码分类可机械判断的错误，再向模型提供目标、硬约束、新事实、失败证据和前后计划差异；同时限制修正次数。p7–10 用 Try/Confirm/Cancel 类比前置验证与恢复，p11正文也保留了作者尚未实践的想法，不应把整段视为生产实证。

应采用“保持目标和授权不变、只修有证据的问题”。不采用“超时一律重试”：请求一旦 sent 而结果未知，重试可能重复计费或副作用。Try 也可能产生付费调用，不能绕过预算；Confirm 必须重新检查权限、资源版本和时效。这里的 TCC 类比不自动提供跨外部系统的事务或回滚能力。

**现状映射。** `backend/service.py:557` 的 `propose_replan()` 只接受受控可恢复检查点，并限定 `ARTIFACT_PUBLICATION_FAILED`；候选计划和证据均由平台构造。`try_replan()` 是这一窄路径的验证，不是 DSH 的自动纠错引擎。DSH 的 `submit_findings` 纠正是同一 Run 内的正常模型续轮，走总次数和账本；crossing 的 unknown 不会自动重发。不能因为仓库里有 Replan API，就声称 DSH 已接入通用 Replan。

**建议。** 默认不自动 Replan，以显式错误类别、可信检查点和重新授权后的边界为前提。付款核对优先保留有限纠正和安全失败。没有可靠证据时，与其编造“替代路径成功”，应返回未完成及固定错误类别。

## W07：失败点、根因点和可恢复点是三件事

p1–5 区分错误显现的位置、错误产生的位置、仍可信的回滚点和新计划起点。它要求回溯事实依赖，记录当时的输入条件与候选路径，避免 A 失败改 B、B 失败又回 A。p6–9 把语义假设交给模型、依赖和失效传播交给代码；p10–11 分别衡量根因判断、起点选择、复用与恢复效果。

这对当前故障归因直接有用。`dsh_plan.py:62` 的 `failed_step()` 只是首个未完成步骤，不是根因定位器；首次模型调用前 SDK 初始化失败时，S1 未完成不代表“检索失败”。本轮 HA-0085 的隔离测试中，诊断确认过 SDK initialize 的 20 秒超时；因此 HA-0086 单独提出初始化/运行阶段固定错误分类，不能靠修改 Plan 标签解决，也不能把一次超时直接归咎于 Provider。机器负载可能相关，但尚未证明是根因。

**不做的过度承诺。** 课程的经验比例没有本项目标定；模型给的根因只是待验证假设。metadata-only 事件不能完整重建当时 Prompt；保存摘要不能替代受控检查点。A2 证据续跑尚未实现，旧 seen_clauses、旧“通过”的槽位或预算状态不能直接继承。

将来续跑至少要验证资源哈希、切块器及规则版本、块摘要、Task 意图；历史证据和本轮已提供给模型的证据分开；检查点原子保存；旧 unknown 预留不因开新 Run 而解冻。本文仅重申设计门槛，不把它列为已交付。

## W17：缩短关键路径不等于提高所有任务成功率

p1–3 强调减少不必要的决策、降低依赖深度、对只读独立步骤并行，并将不可逆动作留给检查或人工确认。p4–5 用回放评测和模板版本管理控制优化。这些工程方向有价值，但其中的概率推导需要附加条件。

课程把 19 步、单步成功率 0.95 与 4 层关键路径对比。**如果仍然有 19 个独立且全部必须成功的任务，只是改为四层并行，整体成功率仍是 0.95¹⁹，不会变成 0.95⁴。** 关键路径决定依赖深度和部分耗时；整体成功概率还取决于实际必需任务数、相关性、重试和 AND/OR 汇聚规则。真正删掉不必要的失败机会才可能提高成功率；不能用四个 DSH 展示步骤代替真实模型/工具决策数。

课程递归计算 DAG 深度的示例还需要补环检测、缺失依赖和空计划处理。启发式评分也不是经过标定的成功概率。当前 DSH 是固定四步投影，没有必要为这个示例加入通用 DAG 调度器；按轮合并进展判定已经处理了并行多工具的部分问题。所谓紧急模式不能放宽预算、授权和发布校验。

**可验证的优化。** 比较总模型轮数、工具往返、重复读取、成功与安全失败的分布，而不是只比较计划框图深度。保留长合同、无答案、隐含例外和取消样本，避免为了缩短轨迹而删掉必要证据。

## C17：长合同需要编排与业务规则分层

p1–3 把业务风险定义、示例和审查流程放在 Skill，代码负责解析、切块与编排；p4 逐块输出 JSON 后汇总；p4–5 讨论按估算窗口的 70% 调整块大小与压缩，评论提到跨块复盘。核心启发是把变化频繁的领域规则与稳定的执行约束分开。

不能直接吸收的部分：课程代码在空风险数组时返回“A”；把“A”理解为低风险是本文推断，原文没有明示，也不能据此证明合同安全；没覆盖、没找到证据和确认无风险必须区分。按条号切块不自动保留跨条引用。70% 是估算阈值，不是 Token 上界。压缩、复盘和重试若调用模型，全部需要纳入预算与发送控制；课程示例没有提供足以替代本项目验收的稳定性数据。

**现状映射。** `backend/dsh_context.py` 在组装前后校验调用/结果顺序，保留最新轮和 system/user，较旧工具结果可以替换成编号、摘录和可重新读取的提示；仍放不下就拒发。字符启发式已经明确不是 tokenizer。`invisible_clause_ids` 与仅有旧副本被省略分开，防止反复读取误算进展。它是受控上下文管理，不是完整的法律风险审查或跨条语义覆盖证明。

**下一步。** 阅读 RAG 和安全章节后再决定最小检索优化：优先验证跨条引用是否能定位、无答案能否保持 unknown，以及旧片段省略后能否重新获取必要证据。不直接增加模型复盘轮数，也不把另一个 pi-contract-review 仓库的能力算进 HarnessAgent。
